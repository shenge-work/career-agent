## 2. v1 基线（重构前事实）

| 项 | 事实 |
| --- | --- |
| 运行 | `npm start` → `tools/serve.js`（Node 原生 HTTP，127.0.0.1:8000）；无框架、无构建 |
| 前端 | `index.html` + `css/style.css` + `js/*.js`，约 42 个 `<script>` 顺序加载，IIFE 挂 `window.ResumeXxx` 全局命名空间 |
| 数据 | `data/resumes/index.json` + 每份简历一个 JSON；`data/companies/companies.json`；`data/tracker/seed.json`；旧 `data/resume.json`；浏览器 localStorage 降级 |
| 已有能力 | 双栏编辑、拖拽排序、板块增删、版本历史、主简历/派生简历、公司档案、投递记录与 IM 聊天、飞书 OAuth/同步、AI SSE 代理、BOSS CDP 采集、矢量 PDF 与图片版 PDF、单文件版 / Tauri 壳 |
| 核心资产 | `renderResumeInner()` + 分页吸附 `computePageBreaks()` + `makeCaptureClone()` 三条铁律；约 1500 行命令式 DOM |
| 测试 | `npm test` → `test/run.js`（1426 条断言），以 vm 沙箱加载前端脚本 |
| 缺陷（对多用户而言） | 数据全在共享 JSON / localStorage，无账号、无隔离、无并发写保护；id 由客户端生成；服务级单份 `ai.config.json` |

**决策前提**：新代码全部放 `v2/`，v1 源码一行不改，两套系统可并行运行、逐步对照验收。

## 3. 本机环境实测（2026-11-03，跨会话可复用）

| 项 | 结果 |
| --- | --- |
| 系统 | macOS 26.2 arm64 |
| Node / npm | v22.22.2 / 10.9.7（满足 `>=22.12`） |
| 工具链 | Xcode CLT 在 `/Library/Developer/CommandLineTools`；系统自带 `/usr/bin/sqlite3` |
| 网络 | npm registry、raw.githubusercontent.com 均 200 可达；磁盘剩余 282 GiB |
| 缺失 | `brew` / `docker` / `psql` / `mysql` / `pnpm` / `yarn` 全部未安装 |
| 权限 | `sudo -n` 被沙箱禁止（operation not permitted）；`/opt` 不可写 |
| 端口 | 5432 空闲 |
| Node 22 内置 `node:sqlite` | `require('node:sqlite').DatabaseSync` 不加 flag 即可建表/插入/查询，仅有 ExperimentalWarning |

**结论**：装不了 Homebrew / 系统级 PostgreSQL / Docker；任何需要管理员权限或系统目录写入的方案直接出局。

## 4. 数据库候选方案对比

| 候选 | 实测 / 评估 | 结论 |
| --- | --- | --- |
| 系统级 PostgreSQL 18 | 需 brew / 管理员权限 / 系统目录写入，本机三者皆无 | 放弃（保留为后期目标） |
| `embedded-postgres` | 仅 beta（18.6.0-beta.19）；`@embedded-postgres/darwin-arm64` 解压 337 MB；npm 安装 6m42s 才下到 99 MB，已中止 | 放弃：体积、稳定性、安装时长都不适合内测 |
| `node:sqlite` / SQLite | 零安装、可持久化，实测可用 | 不推荐：与 PG 方言差异大（`jsonb`、`ON CONFLICT`、类型系统、`gen_random_uuid()`），后期迁 PG 要重写 schema 与 SQL |
| **PGlite 0.5.15** | 29 MB、约 1 分钟装完；内核报 `PostgreSQL 18.6 (PGlite 0.5.15) on wasm32-unknown-emscripten`；实测通过 `jsonb` / `gen_random_uuid()` / `ON CONFLICT DO UPDATE` / `JOIN` / 重启后数据仍在（落盘 `pgdata/` 约 38 MB） | **采用**：同方言，后期只换驱动 |

**迁移承诺**：schema、迁移 SQL、查询语句与真 PG 1:1 平移；切库时只把 `drizzle-orm/pglite` 换成 `drizzle-orm/node-postgres`，不改业务代码（详见 [04](./04-运行维护与后续路线.md) 的 P5 步骤）。

## 5. 最终技术栈（方案结论 vs 实际落地）

| 层 | 方案阶段建议 | 实际落地（以 `v2/package.json` 为准） | 差异原因 |
| --- | --- | --- | --- |
| 前端 | React 19 + Vite 7 + TS | React 19 + Vite 8.3.5 + TS + React Router 7（HashRouter）+ TanStack Query 5 | Vite 8 是当前安装版本；HashRouter 避免服务端路由配置，兼容本地回环部署 |
| 后端 | NestJS + TS | NestJS 12.3.2 + Fastify 5 + TS（CommonJS） | Guard 让权限边界显式；`app.inject()` 做 e2e 无需起真实端口 |
| ORM | Drizzle（pg-core，双驱动） | Drizzle 0.45.4 + 手写 DDL 迁移 | 迁移不依赖 drizzle-kit 在线连接；`db:generate` 输出隔离到 `drizzle/generated/` 做漂移比对 |
| 数据库 | PGlite → PG 18 | PGlite 0.5.15（PostgreSQL 18.6 WASM） | 同方言平替 |
| 密码 / 会话 | Argon2id + httpOnly cookie + `sessions` 表 | `@node-rs/argon2` 默认 Argon2id；token 只存 sha256；SameSite=Lax；`revokedAt` / `users.status` 即时失效；TTL 168h | 按方案落地 |
| 角色 | admin / member 两档 | 同；`/api/users` 由 RolesGuard 限 admin | 按方案落地 |
| 校验 / 工具 | zod、Vitest + Playwright | zod 4、Vitest 5.1；**未引入 Playwright**，改用 Node 22 内置 WebSocket 直连 headless Chrome CDP | 本机已有 Chrome 与 CDP 脚本，零新增重依赖；`app.inject()` 覆盖 HTTP 层 |
| 构建配置 | — | `vite.config.mts` / `vitest.config.mts` | `.mts` 规避 CJS 包内 ESM 配置的 Vite 8 兼容告警；Vite 8 默认 oxc，不再给 `esbuild` 选项 |

## 6. 关键架构决策（勿轻易推翻）

1. **前后端全量重写，但 v1 保留**：v1 的 JSON/localStorage/全局命名空间假设与账号体系根本冲突；新系统独立目录，`LEGACY_ROOT` 只读引用 v1 资产。
2. **渲染引擎不重写成 JSX**：原方案是「在 React 里做命令式 DOM 孤岛」，实际落地更进一步——**服务端 vm 沙箱**内按 `index.html` 顺序加载 v1 八个 JS，调 `ResumeEditor.applyImported(payload)` 后取 `preview.innerHTML`，输出独立 A4 HTML。v1 源码零改动、零复制，PDF 契约原样保留。
3. **行级隔离下沉到数据层**：`TenantDb.forUser(userId)` 返回的对象里**不存在不带 userId 的查询方法**，controller 即使漏写过滤也不越权；所有业务表带 `user_id`，主键为 `(user_id, id)` 复合。
4. **图片版 PDF 走真实浏览器**：分页计算依赖真实 DOM 测量，不能放进 vm 沙箱；生成自执行「导出专用页」，用 headless Chrome CDP 真跑一遍并让 Chrome 下载落盘。
5. **≤10 人内测的安全取舍**：不做公开注册 / 邮件找回 / OAuth / 多因子；本机回环监听 + Host/Origin/CSRF 守卫；初始账号 CLI 播种。正式对外部署前必须重新评估（HTTPS、Cookie Secure、出口网关、审计日志）。
6. **AI Key 按账号存服务端**：`apiKey` 永不回传浏览器，`GET` 只给脱敏状态；`PUT` 留空沿用旧值；显式清空配置即停用。
7. **严格黑白灰**：沿用用户长期视觉偏好，v2 全站无其他色相。

## 8. 阶段编号为何不是递增

P0（骨架/认证）→ P1（迁移）→ P2（业务 API）之后，用户说「继续 按照你的建议来」，据建议优先做了 P4（渲染孤岛 + 矢量 PDF），因为「能编辑、能导出」才是可验收的最小可用闭环；随后补 P4b（图片版分页契约），再回到 P2b 第一期（AI + 采集）。编号反映规划顺序，不反映执行顺序。
