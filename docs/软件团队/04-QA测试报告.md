## 4. 四条容易漏的坑 —— 逐条结论（非泛泛「没问题」）

### 4.1 保存成功后不再重复 PUT
**结论：✅ 真的靠 canonical 判脏，不是靠 effect 依赖数组侥幸。**
- 脏判断唯一入口是 `touch(draft)` 内的 `canonical(draft) === baseline`（`editor-autosave.ts` L119），`commit()` 再以「无 pending 则 no-op」双保险（L148）。旧 effect 的 `[draft,id]` 依赖数组已被替换为「每次 draft 变化都 `touch` + 800ms `commit`」，幂等全下沉到状态机。
- `applyJson` / `undo` / `redo` 造成**内容相同**的 `touch` → canonical 相同 → 不设 pending、不发 PUT（单测 #6 末段 `touch(doc('C'))` 后 `calls.length` 仍为 2 实证）。
- 撤销回基线的优化（`touch` 内 clean && 非 error && 非 inflight 时清 pending）有单测 #10 覆盖。

### 4.2 预览恰好刷新一次
**结论：✅ onDrained 只在「队列排空且最后成功」时触发。**
- `onSettled` 成功且 `pending !== null` 时**不**调 `onDrained`，立即 `pump()` 续发（`editor-autosave.ts` L265–269）；仅 `pending === null` 时 `status='saved'` → `emit` → `onDrained`（L270–272）。
- 连续快输（多次 commit）→ 单飞 + 合并：第 1 次成功不刷、第 2 次排空才刷 1 次（单测 #6 断言 `drained()` 先 0 后 1）。

### 4.3 旧请求晚到不覆盖 jsonText
**结论：✅ 工程师确实删了 L782，保存成功路径不再写 jsonText。**
- 全文 grep `setJsonText` 仅 3 处：初次加载 / id 切换（L839）、主题应用（L1121）、textarea 用户输入（L1331）。`onDrained` 与 `onSettled` 均不触碰 jsonText。旧响应晚到只会被 `isStale` 整体丢弃，无任何写 jsonText 的通道。

### 4.4 错误分槽互不覆盖
**结论：✅ saveError 与 error 真正互不覆盖，error 原有 8 个写入点一行未改。**
- `error` 的 8 个写入点逐一核对：`auditM.onError`(L757)、`downloadPdf`(L1051 清空 / L1074 写入)、`downloadText`(L1083 清空 / L1102 写入)、`themeM.onError`(L1126)、`applyJson`(L1137 清空 / L1139 写入)——全部原样保留，无一处被本轮改动。
- 保存错误走独立 `saveError` state（`onChange` 同步 `view.saveError` + `pushSaveError` 供 beforeunload/flush 追加），渲染为独立 `.alert.save-error-line`，与 `{error && <div className="alert">}` 并存。
- 旧保存 effect 里的 `setError('')` / `setError(message)` 两处已删除（grep 无残留）。

### 4.5 离开保护
**结论：✅ 三条子项全部落地。**
- **beforeunload 只在脏态注册、保存成功即解绑**：effect 依赖 `[saveView.dirty, id, pushSaveError]`，`if (!saveView.dirty) return`（L860）；dirty=false 时 cleanup 解绑。
- **「立即保存并离开」失败保持弹窗不跳走**：`handleSaveAndLeave`（L905–918）`await flushAndWait` → `err = c.view().saveError`，有错则 `setSaveError(err); return`（**不** `setLeaveOpen(false)`、**不** `navigate`），无错才关弹窗 + `navigate('/resumes')`。
- **卸载 flush 只在 `isIdle()` 时发一次**：cleanup 内 `if (payload && c.isDirty(payload) && c.isIdle()) bestEffortFlush(...)`（L883），`isIdle() = !disposed && !inflight`，严格避免与在飞 PUT 乱序。

### 4.6 id 切换（/editor/A → /editor/B）
**结论：✅ dispose + 重建 + reset 落地，A 的脏状态/在飞请求不串到 B。**
- 加载 effect（L826–844）检测 `loadedIdRef.current !== id` 且非首次 → `c.dispose()` → `makeController(id)` 重建（transport 闭包绑定新 id）→ `reset(newDraft)` 灌基线，并复位 `saveView`/`saveError`/`leaveOpen`。
- 关键竞态路径已手推：id 变更瞬间 `data` 先变 undefined（`useQuery` key 变化），debounce effect 以旧 draft + 旧 controller 调 `touch`——若 A 干净则 no-op，若 A 脏则设 pending 到 **A 自己的 controller**（transport 绑定 A），随后 A 的 controller 被 load effect `dispose()`，其 800ms 定时器闭包捕获的是已 dispose 的 controller → `commit()` 因 `disposed` 早退。B 的 controller 仅在 `setDraft(B)` 后的下一次 render 被 `touch(B)`（canonical 相同 → 幂等）。**不存在把 A 内容写进 B 的路径**。
- 在飞 PUT 的响应经 `dispose()` 推进 seq 后全部 `isStale` 丢弃；服务端仍落库 A 的最后 draft（期望行为，不回滚）。

### 4.7 React.StrictMode（main.tsx L16）二次挂载
**结论：✅ 生命周期令牌 + queueMicrotask 处理 dispose 竞态，实测安全。**
- `main.tsx` L16 确为 `<React.StrictMode>`。卸载 cleanup（L877–890）用 `token = ++lifecycleRef.current`，`queueMicrotask(() => { if (lifecycleRef.current === token) c.dispose(); })`。
- StrictMode 同步时序 `setup(token=1) → cleanup(token=1，排队 dispose 微任务) → setup(token=2)` 全在一个同步提交内完成，微任务在提交结束后才执行，此时 `lifecycleRef.current === 2 !== 1` → **跳过 dispose**，controller 存活，自动保存不失效。
- 真实卸载：无新 setup，`lifecycleRef.current === token` → 微任务执行 dispose，正常销毁。id 切换的 dispose 由加载 effect 显式负责（不依赖此微任务，避免提前/遗漏销毁）。

**SPA 非受控跳转的 best-effort 边界（设计已明确，非回归）**：
- 侧栏 `NavLink`、浏览器后退/前进、外部 `<a href>`、`window.location` 赋值只走卸载 cleanup 的 `bestEffortFlush`，**不保证 100% 落库、不谎称已保存**（HashRouter + `<Routes>` 非 data router，`useBlocker` 不可用，本轮不改路由架构）。
- 具体窄窗口：若「在飞 PUT + 有更新 pending」时立刻通过侧栏跳转，`isIdle()=false` 使 flush 被跳过，最后一次击键（<800ms 防抖窗口内）可能未落库。该窗口极窄（需在保存进行中且 800ms 内连续输入后立即跳转），属设计 §2.5 明确接受范围。

**极轻微观察项（不阻断、无需返工）**：
1. `LARGE_PAYLOAD_HINT` 文案恒为「请点击状态条『重试』」，但「重试」按钮只在 `error` 态出现。若 >48 KiB 发生在 `editing`/`saved` 态（payload 已/将自动保存，因 `put()` 无体量限制），该提示会指向一个当前不存在的按钮——虽不会丢数据，但文案略有误导。属边缘 UX 措辞，可后续统一。
2. `ConfirmModal` 的 Escape 关闭不受 `busy` 门控：`busy` 期间按 Escape 会先关弹窗，但 `handleSaveAndLeave` 后续仍按结果导航/写错误，无实际危害（既有组件行为，非本轮引入）。
3. `pump()` 与 `commit()` 的 `inflight` 双守卫属防御式冗余（M4/M5 单独变异不红），行为正确，仅提示维护者后续改动时两处需同步。
