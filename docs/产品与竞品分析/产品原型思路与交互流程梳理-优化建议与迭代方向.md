## 1. 结论先行（精简版）

> **一句话**：产品内核已经升维成「以岗位为聚合根的求职数据底座」，但界面仍停留在「功能并列的编辑器时代」——**18 个路由、12 个平铺图标入口、两条并行且未打通的投递链路、一个独立的 AI 试用页**。定位跃迁写进了文档和数据表，还没写进用户每天走的交互链路。

**三个核心判断**

1. **内核已就位，界面未收口**。`applications` 聚合根 + `application_events` 状态流水 + 4 个场景化 Agent 动作 + E2EE 云同步均已落地；但 `ApplicationItem.trackerId` 在前端零使用、`/applications` 与 `/tracker` 两套实体无跳转关系、`resumes.job_id` 与 `applications.id` 弱关联且无外键。「岗位第一公民」在**架构与交互层成立，在物理表结构层只是部分成立**。
2. **主线闭环断在三处**：编辑器里没有 JD 对照面板、没有版本历史入口、没有投递前体检；投递跟进只是被动日期徽章，无通知与首页聚合；AI 是「你去试用的页面」，不是「随叫随到的协作者」（无写作闭环、无质量评测、面试逐字稿分析仍是占位实现）。
3. **反馈与可逆性不成体系**：多数 `useQuery` 用 `data = []` 兜底，接口失败会被渲染成「还没有数据」；10 处 `window.confirm` 与 5 类无确认破坏性操作并存；无 toast、无离开拦截、无埋点，上线后无法复盘。

**推荐主线**：先止血（V0，与 UI 评审 PHASE 0 合并）→ 再收口到岗位（V1，新增岗位工作台 + 仪表盘 + 打通双轨）→ 后深化内容生产与 Agent（V2/V3）→ 最后在触发条件满足时做单一聚合根迁移（V4）。**不建议**本轮直接做数据模型大重构。

**下一步**：请拍板 §9 的 4 个决策点，其中 §9-Q1（是否按岗位收口 IA）与 §9-Q2（双轨实体是合并还是仅前端打通）决定 V1 的范围与是否需要数据迁移。

## 3. 当前原型思路与信息架构

### 3.1 设计意图 vs 实现现状（本报告最关键的一张对照）

| 维度 | 文档设想（目标原型思路） | 实际实现（2026-11-10 代码） | 落差 |
|---|---|---|---|
| 导航心智 | 「按求职流程走」，五块：仪表盘 / 岗位 / 简历库 / 公司情报 / Agent（AI 收敛为贯穿动作） | 64px 图标侧栏，12 个入口**平铺**；`Layout.tsx` 定义的两个分组、`collapsed` state、`toggleGroup()` 全是死代码 | **未落地**：`重设计构思 §2.3` 判为需重构，至今仍是功能并列 |
| 第一屏 | 求职仪表盘：投了多少 / 卡在哪 / 下一步是什么 | `#/` → `Home.tsx` 已有 5 指标卡、该跟进了、漏斗、最近岗位、下一步建议，但**纯前端计算、无 error 态、跟进提醒为被动展示** | **部分落地**：形状有，权威性与主动提醒不足 |
| 岗位聚合 | 一个岗位聚合 JD + 公司 + 简历版本 + 状态 + 面试材料 | `#/applications/:id` 已有状态 6 按钮、JD、话术、匹配+派生、面试复盘、时间线；但**聊天采集/逐字稿在另一条 `/tracker/:id` 链** | **部分落地**：两条链无 UI 打通 |
| 编辑器 | 「内容生产现场」：右侧 JD 对照面板，实时三档标注 + 一键按 JD 重写 | 双栏 A4 预览 + 递归结构表单 + 原始 JSON；有 800ms 自动保存、五态保存条、撤销栈、双版 PDF 导出；**无 JD 对照、无版本历史入口、无体检** | **未落地**：后端 `jd.service.ts` 与 `/jd-analyze`、`/jd-derive` 已就绪，编辑器没开门 |

## 4. 交互流程梳理（主 / 分支 / 异常三层）

### 4.1 八条核心任务流（现状，标注断点）

| # | 链路（页面 → 操作 → 页面） | 断点 / 问题 |
|---|---|---|
| F1 简历生产 | `#/resumes` 新建 → `#/editor/:id` 改字段 → 800ms 自动保存 → iframe 重载预览 → 导出 ▾ 选矢量/图片 PDF → blob 下载 | 编辑器内**无版本历史**（须回简历库）、**无 JD 对照**、**无投递体检**；撤销栈仅会话内存，刷新即丢；全局 Ctrl+Z 覆盖输入框原生撤销 |
| F2 版本恢复 | `#/resumes` 选中 → 右栏版本列表 → 恢复 + `window.confirm` → 服务端先把当前内容存为新版本再写回 | **可逆性做得好**（恢复本身可逆）；但确认方式与其它 Modal 不统一，编辑器内无入口 |
| F3 岗位主链 | `#/applications` 新建 → 自动进详情 → 录 JD / 关联简历 → 6 态推进 → 生成话术 → 匹配+派生定制简历 → `#/editor/:derivedId` → 时间线 | **与 F4 完全无跳转**；`trackerId` 前端零使用；派生简历 `jobId` 默认空 |
| F4 投递链 | `#/tracker` 新建（公司/岗位/平台）→ `#/tracker/:id` → 体检 / BOSS 聊天采集 / 逐字稿 / AI 复盘 | **本页无状态流转**；关联公司背景只读无关联操作；`interview-analyze` 后端返回 `analysis: null` 占位 |
| F5 公司调研 | `#/companies` 新建 → 详情填六维/录入调研条目与 JD → 生成简报（勾选维度）→ 复制/下载 Markdown | 简报是**纯前端 `buildBrief()`**，无 AI、无服务端；内推快速新增后跳 `#/referrals?company=` 是少数跨板块打通的正面样例 |
| F6 内推跟进 | `#/referrals` 新增（15 字段含下次跟进日）→ 卡片显示逾期/3 天内徽章 → 到期**用户手动打开** → 编辑改状态 | **被动提醒**，无通知/定时/角标；首页「该跟进了」也是纯前端计算且不聚合内推 |
| F7 云同步 | `#/sync` 生成恢复码 → 启用（基线全量首传）→ 设备 B 粘贴加入 → 立即同步 → 冲突进 `#/conflicts` → 恢复/忽略 | **恢复码仅显示一次**，关闭页面不可找回（设计如此，需强提示）；停用可恢复；冲突恢复可逆且留底，是全项目**异常设计最完整**的一条链 |
| F8 AI 配置 | `#/account` → AI 模型 → 填 7 字段 → 保存 → 测试连接 → `#/ai` 选模型 → SSE 流式试用 | 未配置时各业务页统一降级为规则/模板（**诚实降级，优点**）；但试用台明确「不承载业务写作流程」，配置完仍无处可用 |

### 4.2 状态机与流转（现状）

| 实体 | 状态集合 | 触发 | 允许操作 | 备注 |
|---|---|---|---|---|

| 冲突快照 | pending / restored / dismissed | 回灌 LWW 落败 / 恢复 / 忽略 | 恢复（新 HLC、留底）、忽略 | 流水与单例表不支持自动恢复，返回 400 |
| 同步状态 | 未启用 / 已启用 / 同步中 / 出错 | enable / run / disable | 停用可逆，本地数据全保留 | 三阶段 pull→push→GC 各自独立游标 |
| 编辑器保存 | idle / editing / saving / saved / error | 800ms 防抖 | 「打印/另存」 | **仅编辑器有保存态**，其它页靠按钮 busy |

### 4.3 场景三层次自检（对照能力 3 的可用性清单）

## 6. 优化建议

### 6.1 方案对比与选型说明（IA 收口，必做的一次取舍）

| 方案 | 实现成本 | 开发复杂度 | 用户体验 | 风险 | 上线时间 | 综合评价 |
|---|---|---|---|---|---|---|
| **A · 只修缺陷，保持功能并列** | 低 | 低 | 中 | 中（定位落差保留，越晚改越贵） | 快 | **不推荐**：能解决「不好用」，解决不了「不像工作台」 |
| **B · 岗位中心「聚合视图 + 保留功能页」** | 中 | 中 | 好 | 低（复用现有 `applications`，零数据迁移） | 中 | **推荐（本期 V1）** |
| **C · 彻底单一聚合根重构** | 高 | 高 | 好 | 高（迁移 + 双写 + 回填校验 + 回滚） | 慢 | **后续演进**：触发条件满足才启动 |

**方案 B 具体做法**：不删任何现有页面；新增一个「岗位工作台」聚合视图（把 JD / 关联简历 / 公司 / 状态 / 时间线 / 聊天采集 / 逐字稿 / 跟进日期收进一页），把 `#/tracker/:id` 收敛为该视图的一个锚点或详情抽屉；用已存在但前端零使用的 `trackerId` 建立双向跳转；导航按「总览 → 岗位 → 内容资产 → 情报底座 → 系统」分组并给图标配文字标签（顺带解决 IA-02）。**零数据迁移、零协议改动、可灰度**。

**推荐结论**：选 B。理由——① 定位文档已明确「岗位第一公民」，但用户当前感受不到，B 用最小改动把主链路显性化；② C 的收益（消除双轨、强约束）要在有跨实体原子操作时才兑现，当前单人单机场景不急；③ A 会让 UI 评审的组件化投入建在旧 IA 上，后续返工。

**不选 A/C 的原因**：A 保留结构性落差；C 需要迁移 `tracker`/`resumes.job_id` 的历史数据，且 PGlite 单进程、迁移须停 dev，风险与当前收益不匹配。

**演进路径（本期 → 后续 + 触发条件）**：本期 B → 后续 C，**仅当**满足以下任一条件才启动迁移：① 出现因双轨导致的跨端/跨表数据不一致且可复现；② 需要按岗位做跨实体原子操作（级联删除、按岗位授权）；③ 计划多用户或共享协作。启动时必须走「预演 → 双写 → 分批回填 → 四项校验（数据量/字段/线上行为/关联体系）→ 回滚预案」，并保留 `pgdata` 备份。

### 6.3 关键页面线框图思路（方案 B 的三块新增/改造）

```
页面：岗位工作台（#/applications/:id 改造为主）
页面目标：让用户在「一个岗位」下完成从看 JD 到复盘的全部动作
布局思路：
- 顶部：面包屑（岗位 / 公司名）+ 当前状态徽章 + 下一步动作按钮（如「该跟进了」）

交互说明：
- 关联简历为空 → 展示「选择或新建」而非空白
- 状态变更 → 时间线追加一条，且「下一步动作」重算
- 聊天采集/逐字稿从右栏 1 次点击进入（复用 trackerId，不新开顶层实体）
- 四态：空（未录 JD 给「粘贴 JD」引导）/ 加载（骨架）/ 错误（重试）/ 边界（超长 JD 折叠 + 全文展开）
```

```
页面：编辑器 JD 对照面板（#/editor/:id 右栏新增 Tab）
页面目标：把「对着 JD 改内容」变成编辑器的默认动作

         「一键派生」明确提示「生成副本，不覆盖母简历」；AI 未配置时仅给规则结果并标注「规则分析」
四态：无 JD → 引导粘贴；分析中 → 进度；分析失败 → 保留原文 + 重试；JD 超长 → 分段抽取提示
```

```

页面目标：打开应用 5 秒内知道今天该做什么
```

| **V2 内容生产** | 一岗一简历 | OPT-05、投递体检、编辑器内版本入口、撤销栈持久化、真 `.docx` 导出 | 编辑器内完成 JD 定制的比例；导出前体检执行率 | 编辑器动作漏斗（JD 分析 → 派生 → 导出） | AI 自动改写正式简历 |
| **V3 Agent 化** | 贯穿式协作者 | OPT-07、求职信、面试准备、AI 质量评测集、字段级反馈与版本关联 | 评测集事实准确率 ≥85%（建议阈值）、AI 结果采纳率、低置信降级触发率 | **AI 结果采纳率看板**（需记录模型/提示/知识版本） | 自主 Agent / 一键海投 / 向量库 |
| **V4 洞察与结构债** | 越用越聪明（条件触发） | 复盘看板（行业/岗位转化、简历版本有效性、平均回复时长）；**仅在 §6.1 触发条件满足时**做单一聚合根迁移 | 复盘看板覆盖 ≥3 个口径明确的指标；迁移四项校验全过 | 求职转化复盘看板 | 公开注册 / 多租户 |

### 7.2 演进路径与触发条件

- **V0 → V1**：V0 验收通过即可启动；V1 与 UI 评审 PHASE 1（令牌化 + 4 个基础组件）**共用同一套组件**，避免先写页面再返工。
- **V1 → V2**：当岗位工作台的「关联简历 / 派生」使用率可观测且 >0（需 OPT-08 埋点先就位），再决定 JD 对照面板的投入深度。
- **V2 → V3**：**必须先有质量评测集、Diff 审阅契约、降级与人工接管路径，才允许 AI 输出进入简历正文**；无评测集不上线 AI 写作。
- **V3 → V4**：结构迁移按 §6.1 三个触发条件判断，属**条件触发而非排期必做**；不触发则 V4 只做复盘看板。

## 9. 关键假设与待确认问题（集中一次，请拍板）

**已按以下假设梳理，均可推翻**：① 用户以单人桌面端为主，移动端本期只要求「可用」不要求「好用」；② 定位以「岗位第一公民」为准（依据 11-04 定位标尺与重设计构思）；③ 无真实用户数据，优先级用相对估算；④ 云同步与组件化按各自既有路线推进，不与本报告范围冲突。

| # | 决策点 | 选项 | 影响 |
|---|---|---|---|
| **Q1** | 是否按方案 B 把 IA 收口到「岗位为中心」？ | A 只修缺陷 / **B 岗位聚合视图（推荐）** / C 彻底重构 | 决定 V1 范围与是否启动迁移；Q1=B 时 Q2 才需要回答 |
| **Q2** | 「投递记录 tracker」与「岗位 applications」如何处置？ | **仅前端打通、保留双实体（推荐）** / 合并为单一实体 | 决定是否触发数据迁移与回填校验 |
| **Q3** | 是否接受 AI 写作闭环（Diff 人工审阅）作为 V3 主线？ | 接受 / 暂缓（保持 4 个场景动作） | 决定是否必须建评测集、字段级反馈与版本关联；不接受则 AI 不进简历正文 |
| **Q4** | 成功指标以什么为准？是否允许做「数据不出本机」的本地埋点？ | 允许本地埋点 / 完全不做埋点（仅工程验收） | 决定 V1 起的每个版本能否复盘；不埋点则需下调所有量化目标为定性验收 |

> 若 Q1~Q4 不即时拍板，本报告建议按「推荐项」继续推进 V0（不依赖任何决策），V1 待 Q1/Q2 确认后启动。
