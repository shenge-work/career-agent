# 竞品三块能力对照与优化建议（v2 对照版）

> 日期：2026-11-04　基线：v2 本地服务器形态（CareerAgent）
> 依据：Reactive Resume ★43.2k / Resume Matcher ★28.5k / OpenResume ★8.9k 三家的**当前实现**，
> 对照 v2 现状，逐块判断「能否借鉴、值不值得改、怎么改」。
> 范围：仅限用户关心的核心能力块——**① 渲染与 PDF 导出　② 编辑区与内容生产　③ 数据与血缘存储**，
> 并补一块 **④ 求职闭环（差异化）**。

> ⚠️ 本文是 2026-09-21 旧版「竞品三块能力对照」的 **v2 重写**。旧版对照的是已退役的 v1 单文件架构
> （serve.js / app.js / file:// 直开），其「存储血缘最该学」「导出暂缓」等结论，在 v2 已有部分被采纳，
> 故重新对照。

---

## 〇、一句话结论

v2 已经**自发采纳了旧版认为「最该学」的存储血缘**（parentId/kind/jobId），并守住了「预览=导出同源」原则。
所以竞品对照的重心要从「补基础」转向「补内容闭环 + 补 v1 曾有的高频能力」：

| 块 | 竞品最佳实践 | v2 现状 | 借鉴价值 | 建议 |
|---|---|---|---|---|
| ① 渲染与 PDF 导出 | 客户端 react-pdf（自由 CSS 受限） | 服务端 vm 沙箱渲染 + 矢量/图片双 PDF | 中（思想已同，格式偏少） | **P1 补多格式导出** |
| ② 编辑区与内容生产 | 预览=导出同源 + 结构化解析 | 双栏 + 结构表单，缺 JD 对照面板 / 撤销重做 | 高（内容闭环缺口） | **P1 JD 对照面板 + 撤销重做** |
| ③ 数据与血缘存储 | parent_id 版本树 + JD 独立持久化 | 已建 `(user_id,id)` 隔离 + `parentId/kind/jobId` | 低（已采纳） | 维持 + 补应用聚合根 |
| ④ 求职闭环 | 三家均弱 | 岗位/投递/公司离散，无聚合 | **高（差异化机会）** | **P0 加 applications 聚合根** |

---

## 一、① 渲染与 PDF 导出

### 1.1 竞品做了什么

- **Reactive Resume / OpenResume**：纯客户端 `react-pdf` 出 PDF（真矢量、文字可选中），代价是**放弃自定义 CSS**（走结构化模板）。
- 两家的「预览 = 导出同源」原则一致：同一棵文档树渲染，所见即所得。

### 1.2 v2 现状（已核对）

| 方式 | 实现 | 特点 |
|---|---|---|
| 矢量 PDF | `pdf.service.ts` 调本机 Chrome `--print-to-pdf` | 文字可选中、矢量；无浏览器→501 诚实降级 |
| 图片版 PDF / 长图 | `image-pdf.service.ts` 经 CDP `DevToolsActivePort` 落盘 | 版式 100% 一致、精确分页；文字不可选 |
| 预览 | v1 渲染引擎在**服务端 vm 沙箱**加载，输出 A4 HTML | 预览与 PDF 同源（共用 `legacy/` 渲染管线） |

**v2 比 v1 更稳**：v1 受「单文件离线、file:// 直开」约束，导出只能在浏览器侧；v2 把渲染搬进服务端 vm 沙箱，
矢量 PDF 不再依赖「前端起服务」，预览/导出契约也更可控。

### 1.3 结论与建议

- **「预览=导出同源」已守住**，这点不用改（竞品与 v2 思想一致）。
- **明确不做 react-pdf**：引入它 = 放弃自由 CSS 排版这唯一的差异化护城河，得不偿失（与《重设计构思》红线一致）。
- **真正该补的是导出格式覆盖**：v2 目前只有 PDF（矢量/图片），缺 v1 曾有的 **Word(.docx) / TXT / Markdown**。
  这是求职者投递刚需，且 v1 已有成熟纯函数可移植，成本可控 → **P1**。

| 优先级 | 动作 | 说明 |
|---|---|---|
| P1 | 移植多格式导出：Word / TXT / Markdown | v1 `export-extra.js` 纯函数可复用；ATS 抓取需 TXT/Markdown |
| 保持 | 矢量 PDF（Chrome 打印）+ 图片版 PDF | 「文字可选中 + 矢量 + 自由 CSS」唯一交集，守住 |
| 明确不做 | react-pdf / 客户端 PDF 引擎 | 与自由 CSS 护城河冲突 |

## 二、② 编辑区与内容生产

### 2.1 竞品做了什么

- **OpenResume**：预览放 iframe 沙箱（样式隔离），PDF 组件化保证预览=导出一致；`feature-scoring` 解析器用特征评分做结构化解析（不靠硬编码正则）。
- **Resume Matcher**：卖点是「母简历 + 贴 JD → AI 生成定制版」，它证明「内容生产」才是付费理由。

### 2.2 v2 现状（已核对）

- 双栏编辑器：左 A4 实时预览（vm 沙箱）、右**结构感知表单** + JSON 兜底、800ms 自动保存（带 `savedAt`、`previewKey++`）。
- **JD 匹配/派生后端已就绪**（`jd.service.ts`：`analyze` / `buildDerivedPayload` / `deriveTitle` / `extractTerms`；路由 `POST /api/resumes/:id/jd-analyze` 与 `/:id/jd-derive`），但**编辑器内没有「JD 对照面板」入口**——匹配能力是「引擎在、门没开」。
- **撤销/重做缺失**：v2 编辑器无撤销栈（v1 有，随 v1 退役未平移）。
- **结构化 PDF 导入解析缺失**：v1 的 `pdf-parse`（字段级抽取）随 v1 退役，v2 目前无简历 PDF 导入解析。

### 2.3 结论与建议

v2 的「编辑区」在工程上比 v1 干净（结构表单替代裸 innerHTML），但**内容生产闭环的关键两块没接**：

1. **JD 对照面板（P1，最高性价比）**：在编辑器右侧挂「已覆盖 / 弱覆盖 / 缺失」实时标注 + 一键按 JD 重写。后端引擎已就绪，只差前端入口——这是把「排版器」变「Agent 工作台」的最短路径。
2. **撤销/重做（P2）**：编辑器的可预期性底线，v1 有、v2 缺，应补回。
3. **结构化 PDF 导入（P2）**：学 OpenResume 的特征评分解析，把「导入一份 PDF」从「重新手打」变「半自动预填」，且坚持「低置信度标黄、绝不臆造」的诚实原则。

| 优先级 | 动作 | 说明 |
|---|---|---|
| P1 | 编辑器内 JD 对照面板（接已有 `jd.service.ts`） | 后端就绪，前端开门；对齐 Agent 工作台定位 |
| P2 | 撤销/重做栈（按简历隔离） | v1 既有能力，平移回 v2 |
| P2 | 结构化 PDF 导入解析（移植 v1 `pdf-parse` 思想） | 学 OpenResume 特征评分；不臆造 |

## 三、③ 数据与血缘存储

### 3.1 竞品做了什么

**Resume Matcher** 把「一份母简历 → 多份岗位定制版」做成数据库里的显式血缘：`parent_id` 指向 + JD 独立持久化（`job_id`）+ Improvement Record 三方关联（母简历+定制版+JD）。这正是「哪种写法拿到面试」反馈回路的数据底座。

**Reactive Resume** 补 `isPublic`/`isLocked`/`version` 字段。

### 3.2 v2 现状（已核对）

v2 **已经采纳了旧版认为「最该学」的存储血缘**：

- 业务表带 `user_id`，主键 `(user_id, id)` 复合；查询一律 `TenantDb.forUser(userId)`，跨用户资源返 404（行级隔离铁律）。
- `resumes` 表有 `parentId`（母简历 id）/ `kind`（`master`/`derived`）/ `jobId` / `jdText`（JD 原文）——**派生版不覆盖主简历，且 JD 随简历库持久化、可回溯到母简历与对应岗位**。
- 版本历史由 PostgreSQL 承载（编辑自动留痕、手动快照永不清、恢复前自动备份可逆），取代了 v1 的 localStorage 版本。

### 3.3 结论与建议

旧版把「存储血缘」列为 **P1 立即做**，v2 已落地，故本块**借鉴价值降为「维持 + 补聚合根」**：

1. **维持现有血缘与隔离**：这是已验证正确的模型，勿动。
2. **补 `applications`（岗位/申请）聚合根（P0）**：当前「一份简历 ↔ 一个 JD ↔ 一家公司 ↔ 一条投递」关系靠零散字段拼，没有独立「岗位」实体。新定位的「第一公民」是岗位，应新增 `applications(id, user_id, company_id, jd_id, resume_id, status, stage, applied_at)`，`tracker` 降为其状态流水，`resumes.parentId/jobId` 改指向 `applications.id`。这是最大一处数据模型改造，越晚越贵（《重设计构思》§2.4）。
3. **分享与权限**：`share_grants` 表已建，但 API 未接——补 `isPublic`/`isLocked` 的数据层已具备，只差 API 与前端门禁。

| 优先级 | 动作 | 说明 |
|---|---|---|
| P0 | 新增 `applications` 聚合根，重构血缘指向它 | 工作流基座 |
| 维持 | `(user_id,id)` 隔离 + `parentId/kind/jobId` 血缘 | 已验证正确 |
| P2 | 接 `share_grants` API（分享/权限） | 表已建，补 API 与门禁 |

## 四、④ 求职闭环（竞品普遍薄弱，恰是差异化）

三家都强在「做一份简历」，弱在「陪一个人走完一次求职」。这正是 CareerAgent 的差异化机会：

- **岗位为第一公民**：以 `applications` 聚合 JD / 简历 / 公司 / 投递 / 面试材料。
- **求职仪表盘**：投递漏斗（已投/已面/已拒/Offer）、卡住的岗位、本周待办、最近活动时间线——让「工作台」立起来。
- **AI 场景化**：改经历、写逐字稿、分析 JD、复盘投递时，带场景上下文唤起 Agent，而非独立聊天页。

这块竞品没有成熟参照，是 v2 应当「自己定义标准」的地方，优先级应高于单纯的功能补全（多格式导出、缩略图等）。

---

## 五、综合建议（按落地优先级）

| 优先级 | 落地项 | 借鉴来源 | 价值 |
|---|---|---|---|
| **P0** | `applications` 聚合根 + 重构血缘 | 自定（竞品弱项） | 高，工作流基座 |
| **P1** | 编辑器 JD 对照面板（接已有引擎） | Resume Matcher 方向 | 高，最短路径变 Agent 工作台 |
| **P1** | 多格式导出 Word/TXT/MD | v1 移植 | 中高，投递刚需 |
| **P2** | 撤销/重做、结构化 PDF 导入、分享 API | OpenResume / 自定 | 中 |
| **保持** | 矢量+图片 PDF、血缘隔离、版本历史 | — | 已正确 |
| **不做** | react-pdf、客户端 PDF、公开云 SaaS | 三家共性 | 与护城河冲突 |

---

## 六、给用户的一句话总结

v2 已经把旧版最看重的「存储血缘」和「预览=导出同源」**自发做到了**，所以竞品对照的重点不再是「补基础」，
而是补两件事：**① 把已就绪的 JD 引擎在编辑器里开门（JD 对照面板）**，以及 **② 用「岗位聚合 + 仪表盘 + 场景化 AI」走出三家都没做好的「求职闭环」**——
后者才是 CareerAgent 真正能立住护城河的地方。多格式导出和撤销重做是 v1 有过、v2 该平移回来的基本功。
