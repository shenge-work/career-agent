> ⚠️ 本文是 2026-09-20 旧版「开源项目借鉴与改造落地方案」的 **v2 重写**。旧版基线为 v1 单文件架构，
> 且把「JD 派生 / 主题模板 / 分享」列为待做；v2 已部分落地这些能力，故重新映射，旧版的 A1-A7 进度快照以本文 §六 为准。

## 二、可借鉴点的逐条映射（抄什么 → v2 变成什么）

> 原则更新为：**只抄思想与数据模型，不抄框架与部署栈**。v2 自身已是 React + NestJS 框架型，
> 但仍与三家栈不同（PGlite/服务端渲染孤岛），故「架构层面一律不学」，只取产品与数据模型经验。

### 借鉴点 1：结构化样式规则（来自 Reactive Resume）→ v2 主题模板系统

- **竞品做对**：把字号/间距/颜色/板块顺序抽象成可序列化 Theme Schema，量产 15 套模板、实时切换。
- **v2 现状**：`theme.service.ts` 已实现 `listThemes` / `applyTheme`，模板系统后端就绪（v1 的 `theme-templates.js` 已平移为服务端能力）。
- **结论**：✅ **已落地（后端）**。前端画廊入口待完全接；本项不再列为待做。

### 借鉴点 2：JSON Resume 生态兼容（来自 Reactive Resume + jsonresume）→ v2 互操作

- **竞品做对**：以 JSON Resume 为数据底座，导入导出无缝，对接 `resume-cli`。
- **v2 现状**：v1 的 `jsonresume-adapter.js` 随 v1 退役未平移；v2 目前无 JSON Resume 适配。
- **结论**：⏳ **待移植（P2）**。v2 数据模型已是结构化（resumes 表），加双向适配器成本低、能锁死可移植性，建议早做。

### 借鉴点 3：Resume Parser 结构化解析（来自 OpenResume，最高价值）→ v2 导入升级

- **竞品做对**：PDF.js 解析已有简历 PDF，识别结构化字段（姓名/经历/技能/教育），而非只存原文。
- **v2 现状**：v1 的 `pdf-parse`（字段级抽取）随 v1 退役；v2 目前**无简历 PDF 导入解析**。
- **结论**：⏳ **待移植（P1，最高）**。把「导入一份 PDF」从「重新手打」变「半自动预填」，是换工具迁移成本的最低点；坚持「低置信度标黄、绝不臆造」的诚实原则。

### 借鉴点 4：AI harness / JD 驱动一岗一简历（来自 Resume Matcher）→ v2 主线 A 的第 3 步

- **竞品做对**：master resume + 贴 JD → AI 生成定制版 + 求职信 → PDF，支持本地 LLM。
- **v2 现状**：✅ **已落地**。`jd.service.ts`（`analyze` / `buildDerivedPayload` / `deriveTitle` / `extractTerms`）+ 路由 `jd-analyze` / `jd-derive`，血缘 `parentId/kind/jobId/jdText` 已落库。**但编辑器内无 JD 对照面板入口**（引擎在、门没开）。
- **结论**：✅ 后端完成；🟡 **前端入口待补（P1）**——在编辑器右侧挂「已覆盖/弱覆盖/缺失」实时标注 + 一键按 JD 重写。

### 借鉴点 5：经历素材库 / STAR 片段复用（来自 Resume Matcher）→ v2 素材库

- **竞品做对**：一份 master 打底，针对不同岗位抽取重组，而非每份简历从零写。
- **v2 现状**：❌ 未做（[重设计构思](../../重设计构思-个人求职Agent工作台.md) §3.8 列为仍缺）。
- **结论**：⏳ **待做（P2）**，与借鉴点 4 天然结合——JD 匹配命中「缺失技能」时推荐库里含该技能的 STAR 片段。

### 借鉴点 6：分享链接 / 在线预览（三家都有，v2 半成品）→ v2 分享能力

- **竞品做对**：Reactive Resume 分享链接可自托管；OpenResume 可分享在线简历；「简历做完得能发给别人看」是刚需。
- **v2 现状**：🟡 **部分（P2）**。`share_grants` 表已建（`src/server/db/schema.ts`），但 **API 未接、前端门禁未做**。v1 的「导出只读分享页（静态 HTML + 水印）」随 v1 退役。
- **结论**：补 `share_grants` 的 API 与「导出分享页」前端入口；守住「无托管后端、已发出的静态页无法远程吊销」的诚实标注。

### 借鉴点 7：AI 多模型直连（来自 magic-resume）→ v2 AI 阶段 2

- **竞品做对**：DeepSeek/Qwen/豆包直连，中文简历场景对国产模型亲和。
- **v2 现状**：🟡 **部分**。`ai_configs`/`ai_usage` 按账号落库、Key 只存服务端、SSE 流式试用台已就绪；但「选中 → 润色 → Diff → 应用 → 撤销」的写作闭环未接（ROADMAP ⏸）。
- **结论**：⏳ 写作闭环待接（Key 到位后）；坚持 AI 五原则（Diff 审阅 / 范围显式 / 可撤销 / 事实护栏 / 可脱敏）。

## 三、落地排期（建议顺序）

> 原则：**先接「引擎已就绪的前端入口」与「v1 可移植的高频能力」，再补新数据模型与闭环。**

| 周 | 落地项 | 借鉴来源 | 说明 |
|---|---|---|---|
| 第 1 周 | **JD 对照面板（接已有 `jd.service.ts`）** + **结构化 PDF 导入移植** | Resume Matcher / OpenResume | 最短路径变 Agent 工作台；换工具迁移成本最低点 |
| 第 2 周 | **多格式导出 Word/TXT/MD（移植 v1 纯函数）** + **撤销/重做** | v1 移植 | v1 有过、v2 该平移回来的基本功 |
| 第 3 周 | **`applications` 聚合根 + 仪表盘** + **STAR 素材库** | 自定 / Resume Matcher | 工作流基座 + 内容弹药 |
| 第 4 周 | **分享 API 接入 + 导出分享页** + **AI 写作闭环** | 三家共性 / magic-resume | 补产品闭环（Key 到位后） |

**明确不做**（延续 [产品评估与演进建议](./产品评估与演进建议.md) §七，防被开源项目带偏）：
1. 不引 **react-pdf / 客户端 PDF 引擎**——放弃自由 CSS 排版护城河，得不偿失。
2. 不做 **公开云 / 多租户 SaaS**——「个人 Agent 工作台」是单人本地。
3. 不做 **通用对话机器人 / 一键海投**——Agent 是场景化动作，投递由人确认。
4. 不因「Agent」改 **数据自持** 定位——数据仍在本机 `pgdata`。

## 四、落地时的工程护栏（承接项目铁律，防倒退）

1. **行级隔离铁律**：每张业务表带 `user_id`，查询走 `TenantDb.forUser(userId)`；新表（如 `applications`）不例外；跨用户资源返 404。
2. **渲染孤岛契约不变**：v1 渲染引擎在 vm 沙箱零改动；改预览/PDF 必重跑「预览=导出同源」契约测试。
3. **断言落失效面**：写完跑**变异测试**（改坏一行 → 断言必须红 → 还原），否则「全绿」可能没测到。
4. **PII 隔离**：提交前 `grep` 扫 PII（真实姓名/公司名），测试数据一律虚构名。
5. **AI 五原则**：Diff 审阅 / 范围显式 / 可撤销（进版本历史）/ guard 护栏（拦截编造数字与公司名）/ 可脱敏——`ai_configs` 已就位，写作闭环不得绕过。
6. **数据可逆**：迁移前 `pgdata` 备份；`applications` 落地先双写后切换，提供回填校验脚本。

## 五、总结

把竞品调研翻译成一句可执行的话：

> **方向已被 v2 印证**——Resume Matcher 的转型证明「JD 驱动一岗一简历」是行业共识，v2 的 `jd.service.ts` 已对齐；
> **存储血缘（parentId/kind/jobId）v2 已自发采纳**；
> **短板要补的是** OpenResume 的结构化 PDF 导入（v2 缺）与多格式导出/撤销重做（v1 有、v2 待平移）；
> **护城河要守住的是** 数据自持 + 版本历史 + 自由 CSS 排版；
> **真正能立住差异化的是** 三家都弱的「岗位聚合 + 仪表盘 + 场景化 AI」求职闭环。

按 §三 排期：**先接 JD 对照面板 + 移植结构化导入（第 1 周）→ 多格式导出 + 撤销重做（第 2 周）→ 岗位聚合根 + 素材库（第 3 周）→ 分享 API + AI 写作闭环（第 4 周）**。
