## 一、调研目标

用户最初要「有一个公司的板块」汇总投递过的公司调研信息，随后在一天内连续追加需求，最终收敛为三个问题：

1. **资料怎么放**：公司背景、团队、融资、竞品、风险、JD、图片、福利、八卦、薪资、自媒体链接、融资时序、战略转型，各归到哪、怎么查。
2. **板块怎么分**：哪些属于「公司」，哪些属于「投递」，边界在哪。
3. **怎么用**：详情页怎么看、搜索怎么命中、简报怎么离线分享出去。

本纪要沉淀的是「调研发现了什么、结论是什么、还缺什么」，具体字段与验收标准以 D7 设计文档为准。

## 三、现状盘点与关键发现

### 3.1 板块职责混淆（已解决）

早期公司板块同时承载「公司调研」和「投递状态（投递日期 / 是否入库 / 是否锁简历）」。用户明确纠正：**公司板块只展示已收录公司的所有信息及对应 JD，跟投递无关**；投递平台、状态、IM 聊天归投递板块。

结论固化为四条铁律（D7 §二）：

- 公司侧不出现任何投递状态；
- `applied` 仅作隐藏关联标记，供投递板块自动建档，不对外展示；
- 跨板块只读回链，公司侧不写投递数据；
- `companies.json` 是唯一事实源。

### 3.2 数据不入库（本轮沉淀的直接动因）

`.gitignore` 排除整个 `data/`。已入库的 6 家公司、16 条调研、4 份 JD、22 条聊天消息全部只存在于本地私有目录，仓库里查不到、换机器就丢。

结论：需要一层**可入库、可检索、可 diff 的人类可读快照**，且必须自动生成，避免与事实源双份维护。本轮落地为 `tools/export-company-research.js` + `docs/公司调研/公司情报汇总.md`。

### 3.3 六维覆盖严重不均

| 公司 | 六维覆盖 | 说明 |
|---|---|---|
| Flowtica | 6/6 | 来自 PDF 报告，资料最完整 |
| 雷鸟科技 | 6/6 | 来自 PDF 报告 |
| 平安银行 / 富途 / Anker / 网易 | 0/6 | 仅有 1 条从求职记录整段导入的条目 + 1 份 JD |

结论：**4 家公司缺公司背景资料**，这是下一轮资料采集的第一优先级。同时那 4 条历史条目混有投递上下文，导出快照时已单列「附：历史导入条目」，不计入六维、不作公司背景。

### 3.4 搜索命中不了行业相关词

现有 `industry` 是自由文本（如「AI Agent 硬件 / 智能办公硬件」），`allText()` 做字面拼接，搜「大模型」「芯片」「银行」「AR」无法稳定命中对应类目。结论：受控类目词表 + 别名表 + 旧数据推断，类目（唯一、可聚合）与自由标签不合并。

### 3.5 图片存储是本轮最大技术风险

零后端 + 单 `companies.json` + localStorage 5MB + `file://` 直开四者叠加 → 图片不能内联进 JSON。建议 `data/companies/media/<id>/` + `serve.js` 同源静态托管（同源才能被 html2canvas 截图），单文件版降级外链 / 占位。**写第一行代码前必须拍板**，否则数据结构返工。

### 3.6 图片简报无需新增依赖

项目已有本地 `vendor/html2canvas.min.js`（图片版 PDF 管线在用），离线可用。易漏三点：导出强制浅色底（暗色主题黑底不适合外发）、外链图污染 canvas 需归一为同源 / data URI、长图分块且字号放大到手机可读。

## 四、维度体系（调研结论）

用户口述维度经整理后分为三层，下表是最终归类的结论，**各类内容按数据类型独立成数组，不塞进 `research[]`**：

| 层 | 内容 | 建议字段 | 数据类型 | 对外简报 |
|---|---|---|---|---|
| 基础 | 公司简介 / 团队 / 盈利 / 融资 / 竞品 / 风险与挑战 | `research[]`（已有，按 `dim` 分区） | 长文本 + 来源 | 默认包含 |
| 基础 | 行业分类 + 相关行业名词检索 | `industryCategory` / `industryAliases` + 词表 | 受控枚举 | 包含 |
| 基础 | 岗位 JD 索引 | `jds[]`（已有，仿 BOSS 信息架构） | 结构化卡片 | 可勾选 |
| v2 | 公司图片 / 相册 | `media[]` | 媒体文件 | 可选（需同源化） |
| v2 | 福利制度 | `benefits[]` | 结构化「有 / 无 / 不详」表 | 包含 |
| v2 | 公司八卦 / 风闻 | `rumors[]` | 未证实文本 | **默认排除**，勾选加水印 |
| v2 | 平均薪资 + 低位 / 高位 | `salaries[]` + 区间 SVG | 数值样本 | 包含 |
| v2 | 自媒体链接（公众号 / 小红书 / 知乎等） | `links[]` | 内容资产索引 | 包含（附正文快照） |
| v2 | 连续融资情况 | `fundingRounds[]` | 带时间事件序列 | 包含 |
| v2 | 业务战略转型 | `strategyPhases[]` | 带时间事件序列 | 包含 |
| 建议补 | 我的判断 / 决策结论 | `verdict` | 结构化结论 | 简报第一段 |
| 建议补 | 面试与面经 | `interviews[]` | 结构化记录 | 可勾选 |

关键判断：

- **薪资按岗位族分箱**，不做公司整体平均（会误导）；并与 JD 薪资 / 福利做「招聘方口径 vs 员工口径」对照。
- **两张时序图**用结构化事件 + 原生内联 SVG、纯灰阶，**不替换**原文本调研，靠 `SourceRef` 关联共存；融资用阶梯累计图 + 轮次时间线，转型用阶段横条 + 产品 / 收入 / 客户三泳道（传闻阶段虚线）。
- **风闻与正式调研虚线隔离**，默认不进对外简报。
- **链接是内容资产索引**（公众号文章存正文快照），不是「某条调研的出处」。

## 五、我认为还应补充的（按价值排序）

### A. 求职决策闭环 —— 最该补

现在档案库是「资料堆」：看完简介、融资、薪资、八卦之后，没有地方落下结论。建议 `verdict`：推荐度（优先投 / 可投 / 观望 / 不投）、关注点、风险红线、期望薪资与谈判底线、**待核实问题清单（面试要问什么）**、对应哪版简历。这也是简报最该输出的第一段。

### B. 面试与面经

「面试聊什么」目前完全空缺：轮次、形式、真题、面试官风格、反馈、offer 时效。面经又是自媒体链接里最高频的内容类型，应与 `links[]` 双向关联。

### C. 情报质量三件套

- **信息新鲜度**：每条标「N 个月前」，>6 个月标「可能过期」；融资 / 团队 / 薪资变动快，过期情报比没有更危险。
- **来源冲突标记**：官网写「弹性工作」、脉脉写「大小周」要**并排展示**，不覆盖、不自动判赢。
- **统一 `SourceRef`**：相册 / 福利 / 八卦 / 薪资 / 链接 / 调研 / JD 七处都有来源，各写一套必然各自演化；抽象一次全站复用，简报脚注可自动汇总引用数。

### D. 结构与治理

- **通用 `TimelineEvent`**：融资轮次、转型阶段、面试轮次、舆情事件本质都是「带时间的事件序列」，抽一个通用结构 + 横向时间轴渲染器，别每种图各画一套 SVG。
- **口径字典**：金额单位、币种、薪资周期（月薪 / 年薪 / 薪数）、日期粒度在录入时下拉选择，否则图表根本不可比。
- **待核实问题清单**：把「不确定」显式记录下来，避免把传闻当结论。

### E. 明确不做（防范围膨胀）

不接第三方实时薪资 API；不记录可识别到具体个人的负面八卦；不做组织架构图编辑器 / 多人协作 / 云同步；不恢复任何投递状态（铁律不变）；不引入彩色强调（严格黑 / 白 / 灰）。
