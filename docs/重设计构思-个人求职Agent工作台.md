# 重设计构思：从「简历工具」到「个人求职 Agent 工作台」

> 状态：构思稿 · 待评审
> 日期：2026-11-04
> 前置阅读：[00-产品定位与评审标尺](./需求文档/00-产品定位与评审标尺.md)、[00-需求总览](./需求文档/00-需求总览.md)、[ROADMAP.md](../ROADMAP.md)

---

## 〇、一句话结论

当前项目的「定位标尺」仍是 v1 时代的旧定位——**「一份数据可自持的简历排版 + 投递工具」**，
而你已经把它升维为 **「个人求职 Agent 工作台」**。这不是改个名字，而是**产品重心从「排版工具」转向「求职工作流 + 智能体」**的一次定位跃迁，因此需要一次系统性的重设计与改造，而非在旧标尺上打补丁。

本文回答三个问题：
1. **哪里需要重新设计 / 改造**（现有资产与新定位的错位）
2. **哪些能力现在还没有**（新定位要求、但当前产品缺失的）
3. **改造的先后顺序与护栏**（先做什么、守住什么、明确不做什么）

---

## 一、定位的升维：旧标尺 vs 新定位

| 维度 | 旧定位（v1 标尺） | 新定位（Agent 工作台） |
|---|---|---|
| 产品本质 | 简历**排版 + 投递工具** | 求职**全流程工作流**，AI 是协作者而非功能 |
| 核心资产 | 自由 CSS 排版引擎 | 求职数据底座（简历/公司/投递/素材）+ Agent 编排 |
| 用户的心智 | "我来排版" | "我来定目标，Agent 陪我推进求职每一步" |
| 主场景 | 打开编辑器编一份简历 | 一个岗位从「看 JD → 定制简历 → 投递 → 面试 → 复盘」的闭环 |
| 与 AI 的关系 | AI 是"润色"这类**锦上添花**功能 | AI 是**贯穿全流程的主线**，是"工作台"而非"按钮" |

**旧标尺六条护城河里，有三条已经随 v1 退役而失效**（file:// 直开、单文件离线 HTML、Tauri 桌面），
剩下的护城河（自由 CSS 排版、数据自持、版本历史）依然成立，但需要**重新确认它们的位次**——
在新定位下，**「数据自持 + 版本历史」的重要性上升**（它们才是 Agent 反复读写数据的信任基础），
而「自由 CSS 排版」从"唯一主角"降为"能力之一"。

## 二、需要重新设计的现有资产（改造清单）

> 按「错位严重程度」排序，每一处都给出「现状 → 问题 → 改法」。

### 2.1 产品定位文档（最高优先级，先改这个）

- **现状**：`00-产品定位与评审标尺.md` 整篇还在讲 v1 的六护城河，且与 README 的
  "本地服务器形态" 已矛盾（文档说"不做账号体系"，代码却是账号 + 行级隔离）。
- **问题**：标尺失准，会导致后续每个需求的评审都跑偏。评审四问里"是否守住六大护城河"已经答不上来。
- **改法**：重写这份标尺，明确新定位、重排护城河位次、重写"评审四问"为对齐 Agent 工作台的版本，
  并把"明确不做"更新为 v2 时代的红线（README 需求文档索引里已经有一版零散的失效标注，应收拢到此）。

### 2.2 产品命名与门面（✅ 已定稿 CareerAgent）

- **现状**：`package.json` name 原为 `resume-studio-v2`，README 标题「简历工作室（Resume Studio）」，
  目录名 `resume-builder`，`main.ts` 启动日志 / `index.html` `<title>` / `Layout.tsx` 侧栏品牌均为
  "Resume Studio"，favicon 为字母 "R"。名字处处强调"简历"，与"求职 Agent 工作台"定位不符。
- **问题**：「简历工作室 / Resume Studio」把产品钉死在"做简历"这一环，而新定位是"陪一个人走完求职全程"。
  名字是定位的"第一句自我介绍"，不改则新定位无法在用户心智里立住。
- **定稿（2026-11-04）**：**CareerAgent**（中文副标「个人求职 Agent 工作台」）——强调 Agent 属性，
  英文名简洁通用、利于后续可能的英文场景；中文沟通里仍称「求职 Agent 工作台」。
- **落地范围（门面位置已同步，目录名/git 仓库名单独排期）**：
  | 位置 | 现状 → 改后 |
  |---|---|
  | `package.json` `name` | `resume-studio-v2` → `career-agent` |
  | `package-lock.json` | 同步 `career-agent` |
  | `README.md` 标题 + 简介 | 简历工作室 → CareerAgent · 个人求职 Agent 工作台 |
  | `index.html` `<title>` + favicon | Resume Studio / 字母 R → CareerAgent / 字母 C（indigo） |
  | `Layout.tsx` 侧栏品牌 | Resume Studio → CareerAgent |
  | `Login.tsx` 品牌 + 副标 | Resume Studio /「您的简历定制助手」→ CareerAgent /「您的求职 Agent 工作台」 |
  | `main.ts` 启动日志 | Resume Studio API → CareerAgent API |
  | `company-intel.ts` 简报落款 | Resume Studio → CareerAgent |
  | `LICENSE` | resume-builder contributors → CareerAgent contributors |
  | 目录名 | `resume-builder` → 待定（git 仓库名同步，牵连 IDE 路径/他人 clone，单独排期） |
  | `ROADMAP.md`「改名 Resume Studio（暂缓）」 | 已定稿 CareerAgent，移除暂缓标注 |
- **历史文档说明**：`docs/` 下大量 v1 时代的旧设计文档/构建说明/验收记录里的 "Resume Studio"、
  `resume-studio`、`resume-builder` 属**已退役过程存档**，不随本次改名批量改写（改了反而丢历史上下文）。

### 2.3 信息架构（IA）与导航

- **现状**：HashRouter 路由为 `#/login` / `#/resumes` / `#/editor/:id` / `#/companies` /
  `#/tracker` / `#/account` / `#/ai`，是一个**"功能并列"**的侧边栏。
- **问题**：新定位下的心智是**"按求职流程走"**，而不是"在几个互不相干的功能里切换"。
  现在的导航把「简历 / 公司 / 投递 / AI」平铺，用户感受不到"一个岗位的完整旅程"。
- **改法**：以**「岗位（Job）为第一公民」**重组导航。理想 IA：
  - **仪表盘（Dashboard）**：全局视图——投了多少、卡在哪、下一步是什么（见 3.1）
  - **岗位（Jobs/Applications）**：以"一次求职"为单位，聚合 简历版本 + JD + 公司 + 投递状态 + 面试材料
  - **简历库（Resumes）**：母简历 + 素材库，作为"内容资产"而非主入口
  - **公司情报（Intel）**：保持独立（它是跨岗位复用的底座）
  - **Agent / AI**：从"独立页"收敛为**贯穿各页的智能操作**（见 2.6）

### 2.4 数据模型：缺「岗位（Application）」这一层

- **现状**：现有表 `resumes`（含 `parentId/kind/jobId/jdText` 血缘）、`companies`、`companyJds`、
  `tracker`（投递记录）。血缘散落在 `resumes.jobId` + `tracker` 上，**没有一张独立的"岗位/申请"表**。
- **问题**：新定位的"第一公民"是岗位，但数据模型里岗位是隐形的——
  「一份简历 ↔ 一个 JD ↔ 一家公司 ↔ 一条投递记录」的关系靠零散字段拼，无法承载
  "一个岗位的完整旅程"（JD → 简历 → 投递 → 面试逐字稿 → 复盘）。
- **改法**：新增 `applications`（岗位/申请）作为聚合根，重构血缘：
  - `applications(id, user_id, company_id, jd_id, resume_id, status, stage, applied_at, ...)`
  - `tracker` 由"顶层实体"降为 `applications` 的**状态流水**（每次状态变更追加一条）
  - 派生简历 `resumes.parentId/kind/jobId` 改指向 `applications.id`，血缘更清晰
  - 这是**最大的一处数据模型改造**，需谨慎迁移（见 4.2）

### 2.5 编辑器：从"排版现场"转向"内容生产现场"

- **现状**：双栏编辑器（左 A4 预览 + 右结构表单 + JSON 兜底），重心是排版。
- **问题**：新定位下，编辑器的高频动作是**"基于 JD 改内容"**，而非"调字号间距"。
  但 JD 匹配分析、JD 派生（一键定制版）还在 ROADMAP 待办，编辑器里没有任何"对着 JD 写"的能力。
- **改法**：编辑器右侧增加 **「JD 对照面板」**——粘贴/选择 JD 后，实时标注"已覆盖 / 弱覆盖 / 缺失"，
  并提供一键"按 JD 重写该条经历"的 Agent 操作（依赖 3.2 的 JD 匹配 + AI 能力）。

### 2.6 AI：从"独立页"到"贯穿式 Agent"

- **现状**：AI 是一个独立的 `#/ai` 试用台 + 按账号的配置页，是"一个功能点"。
- **问题**：这与"Agent 工作台"是根本矛盾——Agent 不该是一个你去"找它聊天"的页面，
  而应该**在需要的地方随时被唤起**（改经历、写逐字稿、分析 JD、复盘投递）。
- **改法**：AI 层从"页"降为"能力"，设计一个**全局 Agent 上下文**：
  - 保留底层转发 + Key 管理（这是好的，勿动）
  - 新增**场景化智能操作（Agent Actions）**：在编辑器、JD、投递、面试各处挂"让 Agent 帮我…"
  - 每次操作都带上**场景上下文**（当前简历片段 / 当前 JD / 当前投递记录）作为 system prompt 注入

## 三、当前还没有、但新定位要求的能力（新增清单）

> 以下按"新定位的刚需程度"排序。标注「已有种子」= 数据模型/代码已有落点，只需接业务。

### 3.1 求职仪表盘（Dashboard）—— 最缺的第一块拼图

- **痛点**：现在打开应用，用户看不到"我求职进展到哪了"。投递、简历、公司各自为政。
- **价值**：这是"工作台"之所以叫"工作台"的东西——一个**总览**回答三问：
  投了多少 / 卡在哪 / 下一步该做什么。
- **形态**：聚合卡片——投递漏斗（已投 / 已面 / 已拒 / Offer）、卡住的岗位（投了 N 天无回复）、
  本周待办（跟进、面试准备）、最近活动时间线。
- **依赖**：`applications` 表（2.4）落地后才有数据聚合的基础。

### 3.2 JD 匹配分析 + JD 派生（✅ 已实现，是"Agent"的核心引擎）

- **现状（已订正）**：**已实现**。`business.service.ts` 的 `analyzeJd` / `deriveResumeFromJd` +
  `jd.service.ts`（`analyze` / `buildDerivedPayload` / `deriveTitle` / `extractTerms`），
  路由 `POST /api/resumes/:id/jd-analyze` 与 `/:id/jd-derive`，血缘字段 `parentId/kind/jobId/jdText` 已落库。
- **价值**：这是"一岗一简历"的主线能力，也是 Agent 生成定制简历的**判断引擎**（先诊断再生成）。
- **待补**：① 前端编辑器里目前**没有「JD 对照面板」**——匹配分析能力是后端就绪、前端缺入口（见 2.5）；
  ② 派生简历与「岗位（application）」尚未打通，`jobId` 只是游离文本，未指向统一岗位实体（见 2.4）。

### 3.3 投递体检（Audit）—— 投递前的"质检员"

- **现状**：v1 `audit.js` 未移植（页数 / 完整性 / 量化 / ATS 友好度 / 敏感信息三级检查）。
- **价值**：投递前的质量把关，是 Agent 工作台里"防呆"的一环，也天然是 AI 诊断的落点。
- **形态**：投递/导出前自动跑一次，给出可点选的修复建议（部分可直接让 Agent 修）。

### 3.4 面试准备闭环（已有种子，但缺"逐字稿"载体）

- **现状（已订正）**：**尚无载体**。`BusinessService` 里**没有** `analyzeInterview` 方法
  （此前误记为"已留桩"，以代码为准该方法不存在），面试逐字稿/复盘是**全新开发**。
- **问题**：面试材料目前**挂在投递记录（tracker）而非岗位（application）维度**，且缺
  "自我介绍 / 项目逐字稿 / 常见问答 / 复盘笔记"的成体系载体。
- **形态**：挂在 `application` 维度下的——自我介绍、项目逐字稿、常见问答、面试复盘笔记。
  详见 [N12-RAG与Agent求职工作台](./需求文档/N12-RAG与Agent求职工作台.md)。

### 3.5 求职信（Cover Letter）生成

- **现状**：`N7` 覆盖但未做；v1 有纯函数可移植。
- **价值**：投递闭环的关键一环，且是 Agent"按 JD + 简历"生成的天然场景。

### 3.6 投递后的跟进与提醒（Agent 的"记忆"）

- **现状**：投递记录有 `status`，但**没有"什么时候该跟进"的时间维度**。
- **价值**：Agent 工作台的核心价值之一是"替你记住该跟进了"。这是现在完全没有的。
- **形态**：投递时记录 `applied_at` + 可选 `follow_up_after`，仪表盘/通知里提示"该跟进了"。

### 3.7 复盘与数据洞察

- **现状**：没有对"我的求职过程"做任何分析。
- **价值**：让工作台越用越聪明——哪些行业/岗位转化高、简历哪个版本最有效、平均多久有回复。
- **形态**：基于 `applications` + `tracker` 的轻量统计（漏斗、转化率、时间分布），服务端聚合即可，不引重型 BI。

### 3.8 其他已知待办（ROADMAP 已有，非新增，列出对齐）

> ⚠️ 注意：ROADMAP 与 README 的部分"待办"判断已滞后于代码。核对后实际情况是——
> **已实现**：JD 匹配/派生（`jd.service.ts`）、主题模板系统（`theme.service.ts`，`listThemes`/`applyTheme`）、
> 面试逐字稿框架（`analyzeInterview` 留桩）。这些应从"待补"清单移到"已就绪、待接前端/待补闭环"。

真正仍缺的：多格式导出（Word/TXT/MD）、投递体检（`audit.js`）、撤销重做、缩略图仪表盘、
STAR 素材库、分享权限 API 接入、暗色模式切换、对象存储。这些在旧定位下是"功能补全"，
在新定位下应**重新排优先级**（见 4.1），而非照搬旧顺序。

## 四、改造路线与护栏

### 4.1 优先级重排（新定位下的建议顺序）

| 阶段 | 事项 | 理由 |
|---|---|---|
| **P0 定位** | 重写产品定位标尺（2.1）+ **定稿新命名（2.2）** | 标尺错了后面全偏；名字是定位的"第一句自我介绍" |
| **P0 数据** | 新增 `applications` 聚合根（2.4） | 一切"工作流"能力的基座，越晚迁移越贵 |
| **P1 主线** | JD 匹配 + JD 派生（3.2）、投递体检（3.3） | "一岗一简历"的核心引擎 |
| **P1 视图** | 求职仪表盘（3.1） | 让"工作台"成立的第一可见形态 |
| **P1 AI** | AI 场景化（2.6）+ 求职信（3.5） | Agent 从"按钮"变"协作者" |
| **P2 闭环** | 面试准备 + 跟进提醒 + 复盘（3.4/3.6/3.7） | 补全求职旅程的后半段 |
| **P2 门面** | IA 重构（2.3）+ 命名（2.2） | 与数据/能力同频，避免空壳导航 |
| **P3** | 模板系统、缩略图、暗色、分享等 | 旧定位的功能补全，价值后置 |

> ⚠️ 与现有 ROADMAP 的差异：ROADMAP 把「多格式导出」排在第一位，但按新定位，
> 「JD 派生 + 投递体检 + 仪表盘」价值更高、且更贴"Agent 工作台"。建议在 ROADMAP 上同步调整说明。

### 4.2 工程护栏（迁移 `applications` 时的铁律）

1. **迁移走 drizzle 手写 SQL**，新增 `applications` 表 + 把 `tracker` 数据回填为状态流水，
   不破坏现有 `resumes` 血缘，先双写、后切换。
2. **每张业务表仍带 `user_id`**，查询走 `TenantDb.forUser(userId)`，新表不例外（项目铁律）。
3. **跨用户资源返 404**，`applications` 的归属校验与 `resumes` 一致。
4. **测试先行**：`npm test` 为权威，迁移后必重跑 + 变异测试（改动后隔离逻辑必验）。
5. **数据可逆**：迁移前 `pgdata` 备份，`applications` 落地后提供"回填校验脚本"对比新旧血缘。

### 4.3 明确不做（新定位红线，防被带偏）

1. **不做公开云 / 多租户 SaaS**——"个人 Agent 工作台"是**单人本地**的，Agent 是你的私有协作者，
   不做协作、不做公开注册（沿用 v2 决策）。
2. **不做通用 Agent 框架 / 对话式产品**——不把"工作台"做成一个聊天机器人，Agent 是**场景化动作**，
   不是无限对话（避免重蹈"AI 独立页"的覆辙）。
3. **不做自动化"一键海投"**——Agent 帮你准备与跟进，但**投递的最终动作由人确认**（求职是低频高风险的决策）。
4. **不引 react-pdf / 客户端 PDF 引擎、不学 CLI/LaTeX 路线**——沿用旧红线，自由 CSS 排版仍是护城河。
5. **不因"Agent"改数据自持定位**——数据仍在本机 `pgdata`，Agent 的能力不以"上云"为前提。

---

## 五、一句话总结

> 把重心从「**排版一份简历**」移到「**陪一个人走完一次求职**」：
> **重新命名**（简历工作室 → **CareerAgent**）让它名副其实，
> 以**岗位（Application）为第一公民**重构数据与导航，让 **JD 匹配 + 投递体检**成为 Agent 的判断引擎，
> 用**仪表盘**让"工作台"立起来，把 **AI 从独立页收敛为贯穿各处的智能动作**。
> 守住「数据自持 + 自由排版 + 版本历史」三块护城河，明确不做海投与公开云。
