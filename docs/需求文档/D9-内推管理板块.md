# D9 内推管理板块

> 状态：**已完成（2026-11-09）**
> 依赖：D7 公司档案（公司身份与公司名快照）
> 影响面：`referrals` 新表（迁移 0015）、`/api/referrals` 新接口、`#/referrals` 新页面、
> 公司档案详情新增「招聘官网与内推」区块

## 一、问题与定位

原来的求职数据只有两条腿：**公司档案**（这家公司怎么样）和**投递追踪**（我投了哪家、进展如何）。
中间缺一层真实存在、且高度可复用的资产——**内推关系**：谁帮你内推、能推哪个岗位、内推码是什么、
有效期到什么时候、什么时候该去催一句。

内推信息既不属于公司（同一家公司可能有好几个内推人、好几条岗位线），也不属于某次投递
（一条内推可以反复用、可以推多个岗位）。因此单独开板块，不塞进 tracker / applications。

三个板块的分工：

| 板块 | 回答的问题 | 数据源 |
|---|---|---|
| 公司档案 | 这家公司值不值得投 | `companies`（六维调研 / JD） |
| **内推管理（本板块）** | **谁能帮我推、推什么、推到哪一步** | **`referrals`** |
| 投递追踪 | 我实际投了哪些、卡在哪个环节 | `applications` / `tracker` |

## 二、数据模型

新增表 `referrals`（迁移 `drizzle/0015_referrals.sql`），与 `companies` / `company_jds`
同构：`text id + jsonb payload + (user_id,id)` 复合主键。

```
id text            内推记录 id（rf_ 前缀）
user_id uuid       FK users(id)，按账号行级隔离
company_id text    关联公司档案；可空（还没建档，或一个内推人挂着多家）
payload jsonb      内推业务字段（下表）
hlc / device_id / deleted_at   同步三元组，与 0011 完全一致
```

**不加外键到 companies**：companies 主键是 `(user_id, id)` 复合键；且公司档案被删不等于内推关系消失
（内推人还在、岗位链接还有效）。改为删除公司时在 Service 层显式级联软删除，并在 payload 里留
`companyName` 快照，公司档案删掉后内推列表仍可读。

### payload 字段

| 字段 | 含义 | 备注 |
|---|---|---|
| `companyName` | 公司名快照 | 建/改时由服务端从公司档案回填 |
| `referrer` / `referrerRole` | 内推人 / 身份（部门、前同事等） | 与 `position` 至少填一个 |
| `contact` | 联系方式（微信 / 手机 / 邮箱 / 飞书） | |
| `channel` | 渠道：朋友 / 前同事 / 脉脉 / 小红书 / BOSS / 内推码 / 猎头 | 自由文本 + 建议值 |
| `position` / `city` / `salary` | 目标岗位 / 城市 / 薪资区间 | |
| `jobUrl` | 岗位 JD 链接 | |
| `referralCode` / `validUntil` | 内推码 / 有效期 | |
| `status` | 进度 | 见下表 |
| `appliedAt` / `followUpAt` | 内推日期 / 下次跟进日期 | `followUpAt` 驱动「逾期 / 今天 / N 天后」提示 |
| `notes` / `tags` | 备注 / 标签 | |

### 状态机

`pending 待沟通 → contacted 已沟通 → submitted 已内推 → screening 简历通过 → interviewing 面试中 → offered 已录用`
另有终态 `closed 已失效`。口径：`offered` / `closed` 之外都算「进行中」，参与跟进提醒统计。

## 三、公司档案的关联

公司详情页新增 **招聘官网与内推** 区块：

1. **招聘官网链接**：写在 `companies.payload.careersUrl`（jsonb 天然免迁移，历史数据零影响），
   另支持 `referralUrl`（内推表单入口）。保存后顶部 meta 出现「招聘官网 ↗」快捷入口；
   读取侧兼容历史键 `recruitUrl` / `jobsUrl`。
2. **该公司内推列表**：`GET /api/referrals?companyId=` 只读展示，卡片带状态、
   内推人、渠道、跟进日期、内推码、岗位链接，可就地删除。
3. **快速新增**：内推人 / 岗位 / 渠道 / 状态四个字段即可落库，完整字段（内推码、有效期、
   跟进日期、备注）到内推板块补齐。
4. **跳转**：区块标题右侧「在内推板块管理 →」，跳 `#/referrals?company=<id>` 自动过滤。

公司列表卡片同时显示这家公司的内推条数（`内推 N`），公司过滤在接口层完成，前端只做聚合。

## 四、同步与冲突

新表接入既有 E2EE 同步链路，与其余 9 张表同一套语义：

- `drizzle/0015_referrals.sql` 挂载 `ca_business_row_guard()`（统一授时 / 回灌 LWW 守卫）
  与 `ca_record_business_change()`（增量记账，软删除写 delete 墓碑）；
- `sync/engine.ts` 的 `SYNCED_TABLES`、`sync/sync-import.ts` 的 `SYNC_TABLES`、
  `sync/restore.ts` 的 `RESTORABLE_TABLES` 与前端 `Conflicts.tsx` 的 `RESTORABLE`
  一并加入 `referrals`——否则内推数据既不同步、冲突后也无法恢复。

## 五、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/referrals?companyId=` | 列表（省略参数返回全部） |
| POST | `/api/referrals` | 新增，`{ companyId?, payload }`，内推人/岗位至少一个 |
| GET | `/api/referrals/:id` | 单条 |
| PUT | `/api/referrals/:id` | 更新，payload **合并**而非整块替换 |
| DELETE | `/api/referrals/:id` | 软删除 |

跨用户 / 关联到别人的公司一律 404，不泄露资源存在性。

## 六、页面

- `#/referrals`：统计 chips（总数 / 进行中 / 已内推 / 已录用 / 3 天内需跟进 / 覆盖公司）
  → 搜索（公司/岗位/内推人/渠道/内推码/备注）+ 公司筛选 + 状态筛选
  → 左列表右详情/编辑。列表按「进行中优先 → 下次跟进日期」排序，卡片直接给跟进提醒。
- 前端字段规整集中在 `src/web/referrals.ts`（`normalizeReferral` / `followUpInfo` /
  `referralStats` / `careersUrlOf`），页面不重复判空。

## 七、非目标（本期不做）

- 不做内推人通讯录（人 → 多公司的复用关系图谱）；
- 不与投递记录自动对齐（内推成功后可手动建投递，避免两条状态机打架）；
- 不做内推码到期自动失效（只在 UI 提示「有效至」日期）；
- 不做内推奖励 / 返点计算。
