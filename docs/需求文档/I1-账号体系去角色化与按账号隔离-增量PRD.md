## 0. 变更定位（给架构师的一句话）

本地行级隔离（`tenant-db.forUser`）与所有业务表的 user_id 已完备，本次**不动，仅做回归**。本次只改两处：① 身份模型从「admin / member」**去角色化**并移除跨账号管理；② 云端同步的隔离边界从「恢复码 / 保险库」改为「**账号**」，同时保住「同一账号多设备同步」与「E2EE 哑云 + 断云可用」。

现状与目标冲突的四个关键点（仅作定位，非方案）：

| # | 现状 | 与目标的冲突 |
|---|---|---|
| C1 | 建号依赖管理员（首启向导硬编码 admin 且「有账号后永久 409」、`POST /api/users` 需 admin、CLI 带 `--role`） | 移除管理员后建号链路断裂，多账号能力无法自洽 |
| C2 | `VaultRef{vaultId}` 完全由恢复码派生，与登录账号解耦；`SyncEvent`/`SyncEnvelope` 无账号维度，云端按 `vault_id` 分区 | 两个账号填同一恢复码即指向同一云端空间，无法「跟随着账号隔离」 |
| C3 | `pullPhase()` 拉取该 vault 全部事件且回灌时强制改写归属；deviceId 为机器级，同机多账号共享 | A 的云端数据会被写进 B，且「本机事件跳过」判定跨账号干扰 |
| C4 | `UsersService.list()` 是唯一跨账号读取入口；`/account` 成员管理、账号下拉角色标签、文档「管理员统一开号」 | 「设置中没有成员管理」未满足，角色概念仍贯穿产品 |

## 1. 产品目标

**一句话**：把 CareerAgent 从「管理员 / 成员」的准团队模型，回归为「人人平等、每个账号自持本地数据与云端同步空间」的个人本地优先工作台，且云端同步严格按账号隔离。

| 目标 | 可验收成功标准 |
|---|---|
| **G1 身份平权**（产品模型层） | 全产品不存在「角色 / 管理员 / 成员 / 成员管理」概念：任意账号登录后界面、接口、鉴权行为完全一致，无任何跨账号查看或管理能力；且在无管理员的前提下仍可持续创建互相独立的账号 |
| **G2 云端隔离**（数据边界层） | 任意两个账号（同机、同服务、共用同一云端地址、甚至输入完全相同的同步凭证）的本地与云端数据双向零串扰；云端仍只见密文与不透明空间标识，不持有明文身份 |
| **G3 平滑演进**（兼容层） | 同一账号多设备同步能力不回退；存量账号（含原 admin）与历史已同步数据升级无感、零丢失、不要求重建；`npm test` 全绿（基线约 294 通过 / 3 跳过，允许用例数增减，失败数必须为 0） |

## 2. 用户故事

**US-1 个人用户自助拥有账号**
> As 一个只用自己的电脑求职的个人用户，I want 无需任何「管理员」审批或代建就能创建并使用自己的独立账号，so that 我的求职数据完全归我、不受任何人管理。

验收条件：
- 从零安装 → 首启创建第一个账号 → 登录可用，全程不出现「管理员 / 角色」字样。
- 已有一个账号后，仍可自助创建第二个账号，无需任何授权；两个账号数据互不可见。
- 第一个账号对第二个账号没有查看、停用、管理关系；新账号可独立改密、独立启用同步。

**US-2 同一人跨设备同步**
> As 拥有家里与公司两台设备的个人用户，I want 在每台设备登录我的同一账号后接续同步，so that 换设备无缝续用，且云端看不懂我的数据。

验收条件：
- 设备 1 登录账号 A 新增/修改简历与附件 → 设备 2 登录账号 A 启用同步后可见；反向亦成立。
- 升级前已存在的「单账号 + 多设备」同步关系，升级后无需重设凭证即可继续，历史已同步数据可读。
- 云端不可达时两端本地 CRUD 正常，恢复后同步可续、无数据丢失。

**US-3 同一机器 / 同一服务上两个账号互不干扰**
> As 在同一台电脑上分别建「求职」与「副业」两个账号的用户，I want 两个账号的本地数据与云端同步完全隔离，so that 我不会看到对方数据，也不会因为误填相同恢复码而串数据。

验收条件：
- 账号 A、B 同机登录，各自简历、附件、投递、同步事件、同步游标互不出现。
- A、B 即使输入完全相同的同步凭证，云端数据仍互不干扰、不合并。
- A 的同步不会把数据写入 B、不会改写 B 的数据归属，也不会因「同一台设备」跳过 B 应拉取的事件。
- 多个账号共用同一云端服务地址时，上述隔离全部成立。

**US-4 存量用户无感升级**
> As 旧版用户（含被标为 admin 的账号），I want 升级后照常登录、数据不丢、不必重建账号，so that 这次改造对我没有感知负担。

验收条件：
- 原 admin 账号密码不变、可登录、本地业务数据零改动，登录后界面与能力与任何其他账号一致。
- 不强制更换同步凭证、不强制重建同步空间、不要求导出导入。

#### ★ 关键决策展开：账号创建路径（I1-P0-03）

**语义重定义**：账号 = 一个本地独立数据空间 + 一个登录身份。创建账号是**个人自助行为**，不是管理行为；账号之间无隶属、无管理、无可见关系。**不引入任何管理员的替代概念（所有者 / Owner / 主账号）**，所有账号一律平等。

| 路径 | 改造后的产品行为 |
|---|---|
| 桌面首启向导 | 由「设立管理员」改为「创建你的第一个账号」；不再写入任何角色；放开「库里有账号后永久拒绝」，改为无账号时引导创建、有账号时也可继续创建 |
| 登录页 / 侧栏账号下拉 | 新增持续可用的「创建新账号 / 添加并切换账号」自助入口；创建后立即成为独立身份，创建者不能查看或管理它；无角色选择、无邀请码、无邮箱验证、无找回 |
| CLI 建号 | 保留作为本地运维与恢复手段，去掉角色参数 |
| 原「管理员代建 / 停用他人账号」接口 | 取消「代他人建号」与「停用他人账号」语义，仅保留「创建独立账号」的自助能力，不设任何权限差异 |

**边界**：能访问本地服务（含桌面本机）即可建号，不额外设置身份门槛；这属于本地自助建号，**不属于**被 ROADMAP 否决的「对外公开注册服务」。

## 5. 默认决策清单

> 用户已授权自行取舍，以下逐条给出决策，无阻塞性待确认问题。格式为「**默认决策**：…（**理由**：…）」。

### A. 身份与账号创建

- **D1 账号创建方式（最关键）** — **默认决策**：把「管理员代建」重构为「**本地自助建账号**」：首启向导创建第一个账号并去掉角色写入、放开「仅允许创建一次」；登录页与侧栏账号下拉提供持续可用的「创建新账号 / 添加并切换账号」；CLI 建号保留但去掉角色参数；原「代他人建号 / 停用他人账号」能力取消。账号之间无隶属、无管理、无可见关系，所有账号一律平等，不引入任何管理员替代概念。（**理由**：移除管理员后必须保留一条不依赖权限的建号路径，否则多账号能力直接断链；本地优先产品以「能访问本机服务」为所有权边界，自助建号是最小变更，也最贴合「每个账号数据独立」的用户心智。）
- **D2 是否开放公开注册** — **默认决策**：**不开放**。沿用 ROADMAP「⏸ 暂不实施 / ❌ 已否决」结论，不引入公网注册服务、邮箱/手机验证、密码找回、邀请码、第三方登录；本地自助建号不部署为对外账号服务。（**理由**：产品是 local-first 个人工作台，公开注册会引入云端身份体系与托管数据，与 E2EE 哑云语义直接冲突，且用户并未要求。）
- **D3 首启向导「有账号后永久拒绝」** — **默认决策**：放开一次性限制，改为「无账号时引导创建、有账号时也可继续创建」。（**理由**：无管理员后，一次性限制会让第二个账号永远无法创建，与「多账号并存」矛盾；放开是对现有限制的最小修改。）
- **D4 旧 admin 账号如何处理** — **默认决策**：不删除、不降权、不改写数据；原 admin 账号视为与普通账号完全平等的独立身份，登录后 UI 与能力一致，仅自然失去「管理他人」这一已取消的能力。（**理由**：任何形式的降权或迁移都会带来数据风险；用户诉求是「没有管理员」而不是「处置管理员账号」。）
- **D5 是否保留 role 物理字段** — **默认决策**：产品模型彻底移除「角色」概念，任何接口返回、页面展示、鉴权结果都不再读取或依赖角色取值；**物理字段保留 / 置空 / 移除由架构师按最小变更与存量兼容原则决定，产品不强制**。（**理由**：物理列属 DB 迁移范畴，产品只需保证零依赖；把落地方式交给架构师可避免 PRD 越界写技术方案，同时保证存量数据零改动。产品倾向是「暂保留但不读写」，是否物理清理列入 P2。）
- **D6 停用他人账号能力** — **默认决策**：随跨账号管理一并删除，不保留任何账号停用 / 冻结入口（含自助停用自己账号）。（**理由**：该能力是「成员管理」的组成部分，用户明确要求设置中没有成员管理；保留会留下隐性权限模型。）
- **D7 多账号切换** — **默认决策**：支持同一台机器上多账号并存与切换，切换后仅展示当前账号数据。（**理由**：多账号数据独立的前提是能方便地在账号间切换；沿用现有会话机制即可，属最小变更。）

### B. 云端同步隔离

- **D8 恢复码与账号的关系（最关键）** — **默认决策**：由「**解耦**」改为「**绑定**」——同步凭证是账号级凭证，一个凭证只服务于其所属账号；不同账号即使输入完全相同的凭证，也不得合并到同一云端空间、不得互相看到或写入数据；跨设备共享一份数据的唯一合法路径是「在另一台设备登录同一账号」。（**理由**：现状「空间标识完全由恢复码决定且与账号解耦」正是「两个账号填同一恢复码即串数据」的根因，与用户「同步到云端的数据跟随着账号隔离」直接冲突；当前权威设计文档中的解耦决策需标注废弃。）
- **D9 云端是否可持有账号标识** — **默认决策**：**不可**。云端仍为哑云，只见密文与不透明的、账号级但无法反推身份的空间标识；不得存明文账号、邮箱、角色、用户资料或业务明文。「按账号隔离」的对应关系只在本地成立。（**理由**：用户要的是数据隔离，不是让云认识用户；保持 E2EE 哑云是硬约束，隔离不能以「云端知道谁是谁」为代价。）
- **D10 云端隔离的实现手段** — **默认决策**：PRD 只约束**结果不变量**（账号即隔离边界、凭证绑定账号、同账号跨设备可用、云端只见密文、存量同步不中断、断云可用）；密钥派生、空间标识生成、表结构、接口签名一律由架构师定，优先选择不破坏存量同步关系的方案。（**理由**：技术方案是架构师职责；产品锁死不可退让的结果即可避免越界，同时给架构师留出取舍空间。）
- **D11 存量同步数据 / 凭证是否强制更换** — **默认决策**：**不强制**。升级前「一个账号 + 一套凭证 + 多设备」的正常用法，升级后无需重设凭证、无需重建同步空间即可继续同步，历史已同步数据可读且不丢失；若技术方案必须调整，需自行保证该结果，不得要求用户手工导出导入。历史「多账号共用同一凭证」属误用，升级后按各自账号隔离，不自动合并或搬运数据。（**理由**：本地优先产品的数据丢失是红线，正常用户不应为架构改造买单；误用场景不做兜底搬运，避免把串数据的行为固化。）
- **D12 同机设备标识共享** — **默认决策**：产品要求「同一台机器上两个账号的同步事件互不跳过、互不串」，不规定设备标识方案。（**理由**：现状设备标识为机器级，会在「本机事件跳过」判定上产生跨账号干扰；产品只锁结果，手段交架构师。）

### C. 数据边界

- **D13 附件 blob 物理共享** — **默认决策**：不改造。内容寻址的物理去重保留，产品只要求「逻辑上不可见」——任何账号无法通过界面或接口取得不属于自己的附件。（**理由**：现状为物理去重、逻辑不可见，用户诉求是「互不干扰」而非物理隔离；改造会引入不必要的迁移风险。）
- **D14 本地行级隔离** — **默认决策**：不改造，仅做回归验证。（**理由**：`tenant-db.forUser` 与业务表 user_id 已完备，e2e 已验证跨账号 404；重复设计违背最小变更原则。）

### D. 文档与工程

- **D15 权威文档冲突** — **默认决策**：`docs/技术设计方案/云同步技术设计方案.md` 中「恢复码与登录账号解耦」标注为已废弃并改写为「凭证绑定账号」；README 建号示例与「管理员统一开号」表述同步更新；`docs/v2重构归档/` 等历史归档只加废弃标注、不改写正文。（**理由**：权威文档与本次目标直接冲突必须修正，否则后续开发被误导；历史归档保持原貌以免篡改历史记录。）
- **D16 dev 一键登录与 CLI 建号** — **默认决策**：两者保留，dev 一键登录仅用于本地开发，CLI 去掉角色参数。（**理由**：属于本地开发 / 运维工具，不是「成员管理」，删除会降低可维护性且无产品收益。）
- **D17 测试基线中的 admin 断言** — **默认决策**：**改写而非删除**——把「member 403 / admin 200 / 停用后会话失效」等断言替换为「任意账号行为一致、无跨账号管理入口」，并新增按账号隔离用例。（**理由**：直接删除会丢失鉴权回归覆盖，改写能保留测试价值。）
- **D18 单一共享同步服务器地址** — **默认决策**：本次不改造部署形态与服务器运维；隔离必须在「多个账号共用同一云端服务」的前提下成立。（**理由**：用户明确要求「互不干扰」，靠更换服务器实现隔离是伪方案，且部署运维不在本次范围。）

## 6. 范围外（Out of Scope）

1. 不引入 SaaS 化多租户、团队、组织、成员邀请、协作、权限矩阵，也不引入「所有者 / Owner / 主账号」等管理员替代概念。
2. 不开放公网注册、邮箱/手机验证、密码找回、OAuth / SSO、第三方登录。
3. 不在云端存明文业务数据、明文账号身份、用户资料；不把哑云改造成「认识账号的云」。
4. 不重构本地行级隔离、业务表 user_id 模型、PGlite 存储选型；不改简历 / 投递 / AI 等业务功能。
5. 不做账号合并、账号数据迁移 / 导出导入、跨账号共享，以及分享给其他账号。
6. 不改同步冲突解决策略（LWW / HLC）的产品行为，不改会话与密码机制的产品行为（必要的技术调整除外）。
7. 不删除 / 停用任何存量账号，不清空任何存量业务数据或云端已同步数据。
8. 不改同步服务器部署形态、云端地址配置、配额 / 计费 / 设备数限制。
9. 不改写历史归档文档正文，不改 landing / 官网 / 与本次无关页面。
10. 不把「按账号隔离」实现为「云端存储账号名册」——云端零身份是硬边界。
