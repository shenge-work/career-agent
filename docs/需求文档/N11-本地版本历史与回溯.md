# N11 本地版本历史与回溯

> 编号：N11　优先级：P1　借鉴来源：飞书文档版本回溯 / Google Docs 30 天修订历史 / VS Code Timeline（本地历史）/ 快照式+增量式混合存储　状态：待验收（开发完成 2026-09-22）
> 性质：**数据安全 / 核心体验需求**（区别于纯 UI 需求，是「数据自持」护城河的关键补强）
> 调研与可行性验证：✅ 已完成（2026-09-22），结论见 §八

## 一、背景与需求本质

### 1.1 痛点（用户原话转述）

> 每一份简历我都会反复修改，但每次修改**没有版本追踪**。像飞书文档那样，能追踪到这个文档每一次都改了什么、随时回溯到昨天或过去某一次的版本。现在这个项目没有这个能力——万一想找回过去改过的内容，就找不回来了，丢了。

### 1.2 现状（已有能力盘点）

| 已有能力 | 位置 | 边界 / 缺口 |
|---|---|---|
| **撤销 / 重做（undo/redo）** | `js/app.js` `recordHistory/undo/redo` | 仅**会话级**、内存栈（`hist.undo/redo`），**关闭应用即丢失**；上限 `HIST_MAX` 条，超出即丢弃最旧 |
| **飞书版本历史** | `js/views/history-view.js` + `ResumeStore.listVersions/restore` | **强依赖飞书云端**：必须先「上报到飞书」才有版本；未连飞书 / file:// 直开时**完全无版本** |
| **快照能力位（预留）** | `js/store/adapter-local.js` 第 7 行注释 | 明确写着「`versions` 暂 false（快照能力后续接 recordHistory）」——**项目早已预判此需求，但一直未落地** |
| **内容指纹 / 自动同步** | `js/feishu/feishu-sync.js` `contentHash/stableHash` | 已有「内容是否变更」的稳定哈希判定，可复用 |
| **数据源契约** | `js/store/datasource.js` | 已定义 `listVersions(docId)` / `restoreVersion(docId, versionId)` 两个版本接口，本地适配器尚未实现 |

**结论**：版本追踪的**接口契约、快照机制、内容指纹**三大地基都已存在，缺的是「**本地持久化版本历史**」这个核心模块——把 undo 栈从「会话级内存」升级为「持久化、可跨会话、可回溯」的版本链。

### 1.3 需求本质

在**不依赖任何云端**的前提下，为每份简历建立一份**本地持久化的版本历史**：

- 用户每次修改（或自动保存节点）自动落一个版本快照；
- 可随时打开「版本历史」面板，看到「什么时候、改了什么」；
- 可一键回滚到任意历史版本；
- 关闭应用、重启后历史仍在。

## 二、竞品与开源最佳实践（调研结论）

### 2.1 主流简历竞品的做法（大多「绕开」而非「内置」）

| 竞品 | 版本追踪方式 | 评价 |
|---|---|---|
| **Reactive Resume**（★43k+） | **没有内置版本历史**，靠「导出 JSON + 用户自行用 Git 追踪」 | 对普通用户门槛高，本质是「把锅甩给 Git」 |
| **RenderCV**（★17k+） | 「简历即代码」：YAML 文件 + Git 版本控制 | 面向开发者/学术，非可视化编辑 |
| **resume-cli / Awesome-CV** | 同上，Git 管理 `resume.json` / `.tex` | 同上 |
| **Magic Resume** | 本地存储，但未见成体系的版本回溯 | 与本项目同短板 |

**关键洞察**：可视化简历编辑器普遍**没有做内置版本历史**，而是靠「Git / 导出文件」绕开。这恰恰是**本项目的差异化机会**——普通求职者不是开发者，不该要求他们用 Git；「像飞书文档那样一键回溯」才是符合直觉的体验。

### 2.2 成熟产品的最佳实践（非简历领域，可借鉴交互与工程）

| 产品 | 版本历史形态 | 可借鉴点 |
|---|---|---|
| **飞书文档** | 每次编辑自动留痕，右侧「历史版本」列表（时间 + 修订人 + 预览），一键恢复 | **交互范式**：时间线列表 + 版本预览 + 一键恢复 |
| **Google Docs** | 30 天自动修订历史，逐版本 diff 高亮 | 「30 天滚动保留」策略 + diff 可视化 |
| **VS Code Timeline** | 本地文件历史，时间轴视图 | **纯本地**、零云端的持久化实现参照 |
| **Notion Page History** | 自动版本 + 可命名快照 + 回滚 | 手动「命名快照」+ 自动「安全点」结合 |

### 2.3 工程实现模式（前端版本历史的通用解法）

调研 time-travel / undo-redo 系列最佳实践，归纳出三种存储策略：

| 策略 | 原理 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **快照式（Snapshot）** | 每次改动存完整 `{data,fonts,spacing}` 副本 | 实现极简、恢复最快、不易出错 | 每份快照占内存/磁盘 | 中小状态、历史条数可控（本项目简历 payload 通常几十 KB） |
| **增量式（Delta）** | 只存相邻版本 diff | 省空间（可达 90%） | 恢复需重放链条，链断即废 | 大文档 |
| **混合式（Hybrid）** | 每 N 次改动存全量，之间存增量 | 平衡空间与恢复 | 实现复杂度中等 | **本项目推荐** |

**本项目选择：快照式为主、辅以「自动安全点 + 手动命名快照」分层**（详见 §三）。理由：简历 payload 体量小（单份 JSON 通常 10–100 KB），快照式「存完整真相、恢复零推理」的可靠性远大于省那点空间，且与既有 `snapshot()` 函数（`js/app.js:46`，已序列化 `{data, fonts, spacing}`）完全同构，落地成本最低。

## 三、需求描述

### F1 版本快照自动记录（核心）

1. **触发时机**：复用现有 `recordHistory(kind)` 的调用点，在**每次 undo 快照入栈时**，同时向「持久化版本链」追加一条记录。**不做逐字符记录**，沿用既有「同类型短时间（<700ms）连续输入合并」的防抖策略，避免版本爆炸。
2. **记录内容**：一条版本记录 = `{ versionId, timestamp, snapshot（序列化 payload）, label, source }`
   - `label`：来源语义，如 `'编辑'` / `'导入'` / `'重置'` / `'从飞书恢复'` / `'手动快照'`；
   - `source`：`'auto'`（自动安全点）/ `'manual'`（手动命名快照）。
3. **保留策略**：分级保留，兼顾「找回过去」与「磁盘可控」——
   - **全部版本**保留最近 `N` 条（建议 50，可配置）；
   - 超过 `N` 的，按「每天保留首尾 2 条」降采样，最长保留 **30 天**（对齐 Google Docs）；
   - 磁盘兜底：单份简历版本历史总占用超过阈值（如 5 MB）时，自动丢弃最旧的降采样点。

### F2 版本历史面板（交互，对齐飞书范式）

1. **入口**：编辑器顶栏 / 设置页新增「历史版本」入口（复用现有 `history-view.js` 的页面骨架，但目前它只列飞书版本——需改为「**本地 + 飞书**」双来源合并展示）。
2. **列表**：按时间倒序展示版本，每条显示「时间 + 来源语义标签（自动/手动/导入/恢复）+ 可选名称」。
3. **预览**：点选某版本 → 右侧/弹层实时预览该版本的简历渲染效果（**只读**，不污染当前编辑状态）。
4. **回滚**：「恢复此版本」→ 二次确认 → 恢复后**当前内容自动先存为一条新版本**（保证回滚本身也可撤销、不丢当前内容）。
5. **手动快照**：提供「保存为命名快照」按钮，让用户给重要节点（如「投递 A 公司版」「定稿 v2」）打标记，一键定位。
6. **对比**（P2 可选增强）：任意两个版本之间做字段级 diff，高亮「增/删/改」（借鉴 Google Docs diff）。

### F3 存储引擎（跟随主存储后端，不硬编码）

1. **版本历史必须与简历正文同存储后端**，跟随现有 `ResumeLibrary` 的多态后端（native / http+ls / localstorage / memory）走，**不能单独引入 IndexedDB**（否则 file:// 直开、降级场景会分裂）。
2. 具体落点：在 `ResumeLibrary` 内为每份简历维护一个 `versions` 分文档（`{id}_versions`），复用现有 `saveDoc/loadDoc` 通道。native 后端落 App 数据目录、http 后端落 `data/resumes/` 侧文件、localstorage 降级时历史同步降级（并诚实提示「历史仅本次会话内可用」或干脆在 localStorage 配额不足时不记历史）。

### F4 数据源契约打通

1. 实现 `adapter-local.js` 的 `listVersions(docId)` 与 `restoreVersion(docId, versionId)`，把 `capabilities.versions` 从 `false` 改为 `true`。
2. `history-view.js` 改为「先列本地版本，再列飞书云端版本」，来源字段区分 `local` / `feishu`。未连飞书时，历史面板依然可用（本地版本）。

### 边界与异常

| 场景 | 处理 |
|---|---|
| 存储配额不足（localStorage 5MB / 磁盘满） | 静默跳过记历史，并在面板顶部提示「存储空间不足，部分历史未保留」；绝不让异常打断编辑 |
| 降采样/清理时用户正在看该版本 | 被清理版本置灰「已归档」，不可恢复 |
| 恢复过程中崩溃 | 恢复采用「先写当前为新版本 → 再应用目标版本」两步，崩溃最多损失一步 |
| 多份简历 | 版本历史**按简历 id 隔离**，互不串数据（与飞书同步的 `activeResumeId` 分键一致） |

## 四、数据结构

```js
// 每份简历的版本历史文档（与正文同后端，分文档存储）
{
  "docId": "<resumeId>",
  "versions": [
    {
      "versionId": "v_20260922_034012_ab3f",   // 时间戳 + 短哈希，全局唯一
      "timestamp": 1726952412000,              // 记录时刻
      "label": "编辑" | "导入" | "重置" | "从飞书恢复" | "手动快照",
      "name": "投递A公司版",                    // 仅手动快照有
      "source": "auto" | "manual",
      "snapshot": "{data, fonts, spacing, v}"   // 序列化快照（复用 snapshot()）
    }
  ]
}
```

**注意**：快照沿用 `snapshot()` 的 `{data, fonts, spacing}` 口径（`js/app.js:46`），**不包含 `savedAt`**（避免每次保存都因时间戳不同而判定为「有改动」，与 `contentHash` 的剔除逻辑保持一致）。

## 五、验收标准（可量化）

1. **AC1 自动留痕**：连续编辑（间隔 <700ms 合并）每完成一次「输入停顿」，版本历史新增 1 条；导入/重置/恢复等 action 各新增 1 条。
2. **AC2 跨会话持久化**：关闭应用（或浏览器）重新打开，历史版本列表**与关闭前一致**（native / http 后端验证；localstorage 降级场景验证「配额充足时一致」）。
3. **AC3 回滚闭环**：从版本历史回滚到任一历史版本 → 内容精确恢复 → **且回滚前的内容自动成为一条新版本**（可再次回滚回去）。
4. **AC4 无飞书可用**：file:// 直开、未连飞书时，历史面板仍能列出本地版本并回滚（`capabilities.versions=true`）。
5. **AC5 保留策略**：构造 >50 条版本，验证只保留最近 50 条 + 更早的按「每天首尾」降采样、最长 30 天，磁盘占用不超阈值。
6. **AC6 隔离性**：A、B 两份简历各自修改，A 的历史列表不出现 B 的版本记录。
7. **AC7 性能**：100 份版本列表渲染 + 单次回滚在普通设备 <500ms 内完成。
8. **AC8 变异测试**：改坏 `recordHistory` 的合并逻辑 / 快照剔除 `savedAt` 逻辑，对应断言必须变红。

## 六、工程护栏（项目铁律）

1. **不引入任何框架/第三方状态库**——纯原生 JS，沿用现有 `recordHistory` 快照机制，不做重复造轮子。
2. **版本历史跟随主存储后端**，禁止单独引入 IndexedDB / 新存储层（否则破坏 file:// 直开与降级链路）。
3. **快照口径与 `contentHash` 一致**：剔除 `savedAt/id/name` 等易变元数据，避免「每次保存都算新版本」导致历史膨胀。
4. **恢复必须先「当前存为版本」再应用**，保证回滚可逆、不丢内容。
5. **存储失败静默降级**，绝不因记历史失败而中断编辑（对齐「写盘失败静默降 localStorage」既有铁律）。
6. **新增前端模块改四处**：`index.html` script 顺序、`build-single.js` 白名单、`test/run.js` vm 同序、重建 `dist/+dist-desktop/`；拆全局模块第五处 `tools/render-resume.js` vm 沙箱。**验证以 `npm test` 为权威**。
7. **meta 白名单只维护 `META_PASSTHROUGH` 一份**（若版本计数/最后快照时间需进索引，只在这里加）。

## 七、非目标（明确不做）

- **不做**多人协作 / 冲突合并（无后端，天然不支持）。
- **不做**逐字符级编辑重放（不是录屏，是「版本点」回溯）。
- **不做**把完整历史同步到飞书（飞书侧已由「上报版本」形成云端版本，本地历史与云端历史**各管各**，仅在同一面板并列展示，不互相覆盖）。
- **不做**版本历史云端跨设备漫游（那是 N10 多云存储的范畴，且本地历史本质是「本机保险」，跨设备以飞书/N10 云端版本为准）。
- **P2 才做**：版本间字段级 diff 可视化（F2-6）。

## 八、评审结论（2026-09-22，产品经理评审）

**四问结论：**

1. **护城河**：✅ 强相关。本需求直接把「数据自持」从「存得下」升级到「改不丢」，是对可视化编辑器普遍短板的补位——竞品靠 Git 绕开，本项目用「内置版本历史」形成差异化。
2. **价值**：✅ 高。用户明确表达的痛点（改完找不回过去版本），且是**数据安全底线**（不依赖云端也能保命），优先级定 **P1**。
3. **成本**：✅ 低。三大地基（`recordHistory` 快照、`datasource.js` 版本契约、`contentHash` 指纹）全部现成，`adapter-local.js` 已预留 `versions` 位，落地是「补齐本地适配器的两个方法 + 升级 history-view 为双来源」。
4. **依赖**：✅ 无硬依赖。独立于 N10（多云存储），可立即开工；与飞书版本历史并列不冲突。

**评审结论：✅ 通过，定 P1，建议作为下一个可落地项（不依赖 AI Key、不依赖 N10）。**

**与既有需求的关系：**
- 与 **N3（分享与权限）** 的「锁定」互补：锁定态下也应能浏览历史、但不产生新版本。
- 与 **N10（多云存储）** 协同：本地历史是「本机保险」，云端版本是「跨设备保险」，两者在 history-view 并列，构成完整的数据安全网。

## 九、落地记录（2026-09-22，开发完成）

### 实现架构（与 §三 设计的对应）

| 设计项 | 落地 |
|---|---|
| 版本链 = undo 栈的持久化超集 | `recordHistory(kind, label?)` 在 undo 快照入栈的同一刻，把**同款快照**追加到 `ResumeLocalHistory`（js/app.js:111）。回滚版本 = `restoreSnapshot`，与撤销完全同构 |
| 存储引擎（F3） | 新模块 `js/store/local-history.js`：内存缓存 + `_loads` 加载去重 + 400ms 防抖写盘；经 `ResumeLibrary.loadDocRaw/saveDocRaw/removeDocRaw`（新增三个不经索引的底层通道）落 `{id}_versions` 分文档，**不碰 index.json** |
| 保留策略（F1-3） | `applyRetention` 纯函数：≤50 条全保留；更早按「每天首尾 2 条」降采样、30 天窗口；磁盘超 5MB 从最旧降采样点丢弃（`trimByBytes` 绝不动最近 50 条） |
| 数据源契约（F4） | `adapter-local.js` 实现 `listVersions`/`restoreVersion`（映射为 `version_id/create_time/size` 契约形态），`capabilities.versions: !!LH` |
| 历史面板（F2） | `history-view.js` 升级双来源：先「本地版本」（label + 手动/自动徽标）再「飞书云端版本」（云端徽标）；右侧只读预览用 `ResumeRender.buildResumeHtml`（N5 同款受保护交换，零副作用）；「保存为命名快照」入口；恢复走二次确认 |
| label 语义 | 关键 action 调用点显式传入：导入（applyImported）/ 重置（clearSaved）/ 从飞书恢复（pullFromFeishu、restoreFromFeishu）；其余按 kind 缺省「编辑」 |
| 删除清理 | `resumeRemove` / `removeAllResumes` 同步调 `ResumeLocalHistory.removeAll(id)`，不留孤儿分文档 |

### 关键工程决策

1. **单份模式兜底**：`localHistoryResumeId()` 用 `activeResumeId || 'default'`，与历史面板的 resumeId 取法一致。
2. **加载去重（`_loads`）**：`append` 与 `list` 的首次加载复用同一个 Promise，保证「recordHistory 同步返回后立即 list」能看到刚 push 的版本（fire-and-forget 语义下的读写同序）。
3. **模块顺序第五处不需要**：`render-resume.js` 沙箱不加载 local-history.js——app.js 的 `localHistory()` 是运行时惰性查询，缺模块时静默跳过（零回归）。
4. **测试隔离铁律**：cases-local-history 的链路用例**禁止 `ResumeLibrary.create`**（会往共享 index 塞元数据，与 cases-library 的数量断言竞态）；版本历史走 `{id}_versions` 分文档不经索引，直接用字符串 id（`n11-*`）即可。

### 验收结果

| AC | 结果 | 验证方式 |
