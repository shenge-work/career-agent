# 产品定位与评审标尺

> 本文是需求评审的**标尺**：所有需求的取舍，都回到「是否符合本项目护城河、是否对齐真实使用形态」来评判。
> 维护：产品定位变化时更新本文，并同步调整各需求文档的「借鉴合理性」结论。
>
> **2026-11-04 重大修订**：产品定位由「简历排版工具」升维为「个人求职 Agent 工作台」，
> 六条护城河重排，评审四问改写。旧标尺全文见 git 历史（v1 时代）。

---

## 一、本项目是什么（一句话定位）

**一个「个人求职 Agent 工作台」**：以**岗位（Application）为第一公民**，把一次求职的完整旅程——
看 JD → 定制简历 → 投递 → 面试 → 复盘——收敛到一个本地自持的工作台里；AI 不再是某个"功能页"，
而是贯穿每一步、随叫随到的**协作者（Agent）**。数据在本机、按账号隔离、可导出可迁移。

> 与旧定位（"数据可自持的简历排版 + 投递工具"）的区别：**重心从「排版一份简历」移到「陪一个人走完一次求职」**。
> 简历排版仍是核心能力之一，但降为工作台里的"一个模块"，不再是产品的全部。

## 二、六大护城河（评审时逐条对照，守住不丢）

> v2 切换为「本地服务器 + React + NestJS + PostgreSQL」后，v1 时代的护城河有失效、有升位。现重排如下。

| # | 护城河 | 含义 | 为何是护城河 |
|---|---|---|---|
| 1 | **数据自持 + 行级隔离** | 全部数据落本机 `pgdata`（PostgreSQL 兼容），按账号隔离、可导出 JSON 迁移、不依赖任何云端账号 | Agent 反复读写数据的**信任基础**；竞品多锁在云端数据库 |
| 2 | **岗位（Application）为第一公民** | 一次求职 = 一个聚合根，串起 JD + 公司 + 简历 + 投递状态 + 面试材料 + 状态流水 | 让"投了多少/卡在哪/下一步"这类工作台问题有单一数据源；竞品多为功能平铺 |
| 3 | **自由 CSS 排版引擎** | 可颠覆传统布局自由排版，导出与预览同源 | 所有框架型竞品（react-pdf 放弃自由 CSS） |
| 4 | **本地版本历史 + 可逆恢复** | 编辑自动留痕、手动快照永保、恢复前自动备份（可逆） | 由 PG 承接，取代 v1 飞书版本；竞品要么无、要么锁云 |
| 5 | **JD 匹配 + 派生引擎** | 粘贴 JD → 已覆盖/弱覆盖/缺失三档 + 一键生成定制版简历 | "一岗一简历"主线的判断引擎，也是 Agent 生成定制简历的底座 |
| 6 | **场景化 Agent（AI 贯穿式）** | AI 按账号配置 OpenAI 兼容上游，Key 只存服务端；以"场景化动作"而非"独立聊天页"嵌入编辑器/JD/投递/面试 | 让 AI 从"功能"变"协作者"，是本产品区别于"简历工具"的根本 |

> 已随 v1 退役、不再作为护城河：file:// 直开、单文件离线 HTML、Tauri 桌面/安卓壳、飞书同步。

## 三、真实使用形态（决定需求优先级的事实依据）

> 据 `docs/产品与竞品分析/产品评估与演进建议.md` 结论，并随定位升维更新：

真实用法是「**本地为一份份岗位定制简历、并持续跟进投递结果**」。由此推导的优先级原则：

1. **求职闭环（投递/跟进/面试/复盘）> 内容生产（AI/JD 定制）> 排版美化**——排版已是护城河，
   用户最痛是"这个岗位怎么拿下来"。
2. **JD 驱动的"一岗一简历"**是主线：每个岗位都值得一份定制简历 + 一条可追踪的投递旅程。
3. **Agent 的价值在"替我记得、帮我准备"**：跟进提醒、投递体检、逐字稿、复盘，而非"帮我海投"。

---

## 四、评审四问（每个需求都要过一遍）

1. **护城河**：是否守住（或增强）上述六大护城河？是否被竞品带偏（引框架/上云/做通用对话机器人/放弃自由 CSS）？
2. **价值**：是否对齐「岗位为第一公民 + 一岗一简历」的主线？是否让求职闭环更完整？
3. **成本**：是否纯增量、低风险？还是牵动核心渲染/存储/聚合根的破坏性改动？
4. **依赖**：是否依赖其他未完成需求或前置条件（如 AI Key、`applications` 表、对象存储）？

## 五、明确不做（评审红线，踩中即否决/降级）

1. **不做公开云 / 多租户 SaaS / 公开注册**——"个人 Agent 工作台"是单人本地定位，Agent 是私有协作者。
2. **不做通用 Agent 框架 / 无限对话式产品**——Agent 是**场景化动作**，不是聊天机器人（避免重蹈"AI 独立页"覆辙）。
3. **不做自动化"一键海投"**——Agent 帮你准备与跟进，但**投递的最终动作由人确认**（求职是低频高风险决策）。
4. **不引 react-pdf / 客户端 PDF 引擎**——沿用；v2 双版 PDF 走服务端矢量渲染。
5. **不学 RenderCV/LapisCV 的 CLI/LaTeX/YAML 路线**——违背可视化编辑定位（其"简历即代码 + 版本控制"哲学由 PG 版本历史承接）。
6. **不做 Editor 级协作分享权限**——本地单人定位，分享只做只读授权（`share_grants` 已建表）。
