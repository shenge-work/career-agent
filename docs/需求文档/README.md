> 决策，随项目切换为**本地服务器形态**（React + NestJS + PostgreSQL，v2 已是主线）而**失效**；
> 其余各条（不学 CLI/LaTeX 路线、不做协作权限、不引入客户端 PDF 引擎等）继续有效。
> 新架构决策见 [../v2重构归档/01-背景与选型决策.md](../v2重构归档/01-背景与选型决策.md)。

1. ~~**不引入 React/Vue/NestJS/Next.js 框架**~~ → **已失效**：v2 主线即 React + NestJS（本地自托管，非公开云服务）。
2. ~~**不做服务端账号体系 / 不自托管后端**~~ → **已失效**：现为本地服务器 + 账号行级隔离；对外公开注册仍不做。
3. **不引入 react-pdf / 客户端 PDF 引擎**——沿用；v2 双版 PDF 走服务端矢量渲染。
4. **不学 RenderCV/LapisCV 的 CLI/LaTeX/YAML 路线**——违背可视化编辑定位（其「简历即代码 + 版本控制」哲学由 PG 版本历史承接）。
5. **不在 AI 之前继续加导出格式或新平台**——导出重建按 ROADMAP 高优先级分期执行。
6. **不做 Editor 级协作分享权限**——需协作后端；本地单人定位不变，分享只做只读授权。

## 需求文档编写规范

每篇需求文档遵循统一结构，方便开发认领：

```
# <需求名>
> 编号 / 优先级 / 借鉴来源 / 状态 / 评审结论

## 一、背景与竞品参照
## 二、用户价值（痛点 → 收益）
## 三、需求描述（功能点 + 交互细节，含边界与异常）
## 四、数据结构（如涉及存储/schema 变更）
## 五、验收标准（可测试的量化指标）
## 六、工程护栏（项目铁律 + 测试要求）
## 七、非目标（明确不做的范围）
## 八、评审结论（护城河/价值/成本/依赖四问 + 通过/降级/否决）
```
