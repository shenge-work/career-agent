> 日期：2026-11-09

## 1. 背景与问题

用户诉求分三层，由近及远：

1. **当下**：快手社招岗位上传简历后「解析不全」，需手动把简历内容复制粘贴进表单 → 用浏览器自动化代填。
2. **可复用**：把这个流程沉淀成 skill，以后「简历 + 官网」即可自动投递、自动填表单。
3. **项目复用 + agent 化**：能力沉淀到 CareerAgent 项目，做到「内推中一键投递 → 后台全流程自动化」，后期接入 agent 基座/工程化。

本文档回答第 2、3 层：**如何把「投递自动化」做成项目里可复用的能力，并平滑升级到 agent 全流程自动化**。

---

## 2. 核心洞察：投递是「采集」的逆操作

项目在 2026-11-09 已落地 **「数据采集与统一导入」** 框架（见 `docs/技术设计方案/数据采集与统一导入-技术设计方案.md`）：

- **采集侧**（外部 → 本地）：agent 用浏览器自动化/爬虫/API 抓到数据 → 按 `data/import-schema.md` 契约产 JSON → `scripts/import-data.ts` 一行入库。
- **导入侧**：固定、幂等、走正式 HTTP API。

**投递侧**（本地 → 外部）是它的镜面：

```
采集： 招聘官网 ──抓取──▶ 契约 JSON ──导入──▶ 本地 PG（公司/岗位/内推/投递/面经）
投递： 本地简历 ──结构化──▶ 简历字段 ──填表──▶ 招聘官网申请表单
```

两者共享同一套底层能力，可以统一设计：

| 维度 | 采集侧 | 投递侧（本方案） |
|---|---|---|
| 数据结构 | `import-schema.md` 契约 | 简历结构化字段（本方案定义） |
| 浏览器操作 | 爬取/截图/DOM | DOM 填表/点击/上传 |
| 动作性质 | 读（拉进来） | 写（推出去，需确认） |
| 复用点 | 浏览器自动化 skill | 同一浏览器自动化 skill |

**结论**：不要为投递另起炉灶。把「简历结构化字段契约」+「浏览器填表能力」做成与采集侧对称的通用能力，投递只是它的一个应用。

## 3. 现状盘点（已有什么、缺什么）

### 3.1 已有资产

| 资产 | 位置 | 与投递的关系 |
|---|---|---|
| 简历结构化数据 | `resumes` 表（`payload` jsonb）+ v1 渲染引擎 | 投递的数据源 |
| JD 匹配派生 | `D3-JD驱动派生版本` + `parentId/kind/jobId` 血缘 | 投递前「针对岗位定制简历」 |
| 内推管理 | `referrals` 表 + `#/referrals`（D9） | 内推关系 → 一键投递的入口 |
| 投递追踪 | `applications`/`tracker`（D6） | 投递后的状态记录 |
| 统一导入 | `data/import-schema.md` + `import-data.ts` | 投递结果的落库通道 |
| 浏览器自动化 skill | WorkBuddy 内置浏览器 / Chrome 扩展 | 填表的执行器 |
| 投递 SOP skill | `skills/job-apply-automation/`（本次新增） | 投递流程的知识沉淀 |

### 3.2 缺什么（本方案要补的）

1. **简历字段 → 申请表单字段的映射契约**（跨官网标准化的字段清单）—— 已起步，见 skill 的 `resume-field-mapping.md`，但只覆盖快手，需扩展。
2. **投递动作的「执行器」抽象**：现在投递靠 agent 现场操作浏览器（每投一次都要 agent 重新 DOM 定位、滚动、填表），没有可编程的「填表引擎」。
3. **投递结果回写**：投完没有自动把「投了哪个岗位、什么时候」写回 `applications`（目前靠 `import-data.ts` 手动导）。
4. **一键投递的编排**：内推管理板块里有内推关系，但没有「点一下 → 自动打开官网 → 填表 → 投递」的闭环。

## 4. 落地方案（分三阶段）

### 阶段一：把「投递 SOP」固化为可复用 skill（✅ 本次已完成）

产出：`skills/job-apply-automation/`（SKILL.md + 字段映射 + 浏览器踩坑记录）。

- 价值：以后「简历 + 官网」触发，agent 自动按 SOP 走「解析→上传→填表→确认投递」。
- 局限：仍是**人工监督的半自动**——agent 现场操作浏览器，每投一次都要现场定位表单、逐字段填，且最终投递需人确认。

### 阶段二：抽「简历字段契约」+「填表执行器」，让投递可编程（建议下一步）

这是把「一次性 SOP」升级为「项目可复用能力」的关键一跳。拆成两层：

#### 4.2.1 简历字段契约（数据层）

定义一份**投递专用**的结构化字段清单（对标采集侧的 `import-schema.md`）：

```jsonc
{
  "basic": { "name": "", "phone": "", "email": "", "location": "" },
  "workExperiences": [{ "company": "", "position": "", "startDate": "", "endDate": "", "responsibility": "", "achievement": "" }],
  "projects": [{ "name": "", "role": "", "startDate": "", "endDate": "", "description": "", "responsibility": "" }],
  "educations": [{ "school": "", "degree": "", "major": "", "startDate": "", "endDate": "" }],
  "selfEvaluation": "",
  "works": []
}
```

- 来源：`resumes` 表的 payload 已经结构化，可以直接映射出这份字段（简历在库里，不用重新解析 PDF）。
- 落点：新增 `data/apply-schema.md`（投递字段契约），与 `import-schema.md` 并列，形成「采集契约 + 投递契约」对称。

#### 4.2.2 官网适配器（执行层）

每个招聘官网一个「适配器」，定义该官网表单的字段映射 + 填表策略：

```
apply-adapters/
├── kuaishou.ts      # 快手（本次实战已摸清字段名，见 skill）
├── boss.ts          # BOSS 直聘（待适配）
├── lagou.ts         # 拉勾（待适配）
└── ...              # 其他官网按需扩展
```

每个适配器输出两样东西：

1. **字段映射表**：`简历字段 → 该官网表单的 DOM 选择器/name 属性`（本次快手已实测出 name 属性表）。
2. **填表策略**：哪些字段要补、哪些要修正 OCR、日期怎么填、哪些必填。

**关键设计**：适配器只做「映射描述」，真正的 DOM 操作交给统一的「浏览器填表引擎」。这样加一个新官网 = 加一个映射文件，不用重写填表逻辑。

#### 4.2.3 填表引擎（能力层）

一个可编程的填表执行器，输入「简历字段 + 官网适配器」，输出「填好的表单 + 投递结果」。它封装本次实战踩过的坑：

- DOM 快照 node_id 失效重取、先 click 再 type、`Control+a` 全选清空
- 滚动（SPA 内部容器用 PageDown/PageUp）
- 日期选择器（坐标点击易失败 → 非必填留空策略）
- 最终投递按钮的「确认闸门」

这一步的**形态选择**（关键决策，见 §6）。

### 阶段三：接入 agent 基座，后台全流程自动化（远期）

当阶段二的「填表执行器」稳定后，把它挂到 agent 工作流（`Agent-Harness架构调研` 已定的 TS 轻量 loop 路线）：

```
用户在 #/referrals 点「一键投递」
   → 取该内推的岗位 JD + 简历（本地 PG）
   → 意图路由：匹配 JD → 派生定制简历（D3 能力）
   → 填表执行器：打开官网 → 上传简历 → 填表单
   → 投递确认闸门（人审批）
   → 结果回写 applications（复用 import-data 通道）
   → 更新 referral 状态 submitted
```

这一阶段把「投递」变成 agent 的一个**工具（Tool）**，纳入 Supervisor 编排。参考 `Agent-Harness` 文档：工具 = schema + 权限 + 执行，投递工具天然需要「权限审批」层（对应 Codex 的 Guardian / Claude Code 的 permission）。

## 5. 复用方式对比（三种可选形态）

| 形态 | 触发方式 | 自动化程度 | 落地成本 | 适用阶段 |
|---|---|---|---|---|
| **A. 纯 skill（现状）** | 用户在对话里说「投这个」 | 半自动（agent 现场操作） | 已落地 | 当下 |
| **B. skill + 适配器 + 填表引擎** | 「简历+官网」参数化触发 | 半自动（填表自动、投递确认） | 中 | 阶段二 |
| **C. agent 工具 + 编排** | 内推板块「一键投递」 | 全自动（后台跑、人审批闸门） | 高 | 阶段三 |

**推荐路径**：A（已做）→ B（建议下一步）→ C（远期接 agent 基座）。三者是**渐进复用**，不是推翻重来——B 的「简历字段契约 + 官网适配器」会被 C 的 agent 工具直接复用。

## 6. 关键技术决策：填表引擎放哪、用什么实现

### 6.1 执行器选型

本次实战用的是 WorkBuddy 的浏览器自动化（`mcp__browser__*`），它的特点：

- **优点**：能复用 Chrome 已有的登录态（快手的登录 cookie 直接可用，不用处理登录）；DOM 优先操作稳定；WorkBuddy 内置，零额外部署。
- **缺点**：SPA 滚动/日期选择有坑（已记录）；是「人盯式」半自动，不适合后台无人值守全自动。

**决策**：

- **阶段二（半自动）**：继续用 WorkBuddy 浏览器自动化，把 SOP 里的踩坑经验固化成「填表引擎」的操作规范（即 skill 的 `browser-playbook.md` 已做），每投一次 agent 现场执行。
- **阶段三（后台全自动）**：需要**无头、可编程、可重跑**的填表引擎，改用 **Playwright/Puppeteer 脚本**（对应采集侧路线 3「WebDriver 固定脚本」），原因：
  1. 结构稳定的官网招聘页（快手/Moka 等）用固定脚本可重复跑、可 CI 化；
  2. 后台无人值守不能依赖「有人在浏览器里点」；
  3. Playwright 能精确处理日期选择器、下拉、文件上传，避免 DOM 快照/坐标的坑。
- **登录态问题**：Playwright 无头脚本需要处理登录（保存 storageState / 复用 cookie），这是阶段三要单独解决的（反爬/验证码/账号风控）。

### 6.2 反爬与合规边界（必须正视）

投递自动化触碰招聘平台的反爬与账号风控，落地方案必须守住红线：

1. **不绕过验证码/风控**：遇到人机验证（滑块/短信），停下来交给人。
2. **不批量高频投递**：这是「个人求职工具」定位（单账号、投自己的简历），不是「批量群投」。高频会触发风控 + 违反平台协议。
3. **投递动作始终保留「确认闸门」**：真实提交必须人审批，agent 不得全自动投递（对应 SOUL 边界「external action 需谨慎」）。
4. **只投目标岗位**：岗位匹配 + 简历定制（D3）在前，避免海投。

### 6.3 简历数据从哪来

投递的数据源是**本地 `resumes` 表**，不是重新解析 PDF：

- 简历在库里已是结构化 payload，直接映射成投递字段契约，无需 OCR。
- 针对岗位投递时，用 D3 的「JD 派生」先生成定制版简历，再投定制版。

这比本次实战（从资料库 PDF 重新解析）更顺——本次是因为快手投递在 CareerAgent 之外（用户手动在 Chrome 选的岗位），数据没在本地库里。

## 9. 风险与注意事项

1. **反爬/风控**：批量自动化投递会触发平台风控、封号，必须守住「单账号 + 确认闸门 + 不绕验证码」红线。
2. **表单结构漂移**：官网改版会破坏字段映射，适配器要可快速更新（字段映射独立成文件）。
3. **日期选择器**：是填表最大的坑，Playwright 无头方案可解，现场浏览器方案需留空策略。
4. **简历真实性**：只排版不编造，缺失业绩留空（本次丰速两周经历即如此）。
5. **登录态**：后台全自动需要安全的登录态管理（storageState 加密存储），涉及凭证安全。
