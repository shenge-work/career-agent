# 数据采集与统一导入 - 技术设计与落地方案

> 状态：**已落地 v1**（2026-11-09）
> 关联产物：`data/import-schema.md`（契约）、`scripts/import-data.ts`（通用导入器）、`data/inbox/example-import.json`（示例模板）

---

## 1. 背景与问题

CareerAgent 的五类核心数据——**公司、岗位(JD)、内推、投递、面经**——全部来自外部平台，
需要靠爬取/采集获取，再导入本地数据库。目前存在的问题：

1. **采集侧方式多样且持续变化**：WorkBuddy / 豆包 / TeleAgent 等智能体的浏览器自动化、
   AI RPA（影刀 / UiBot / 自研群控）、WebDriver 固定脚本（Playwright / Selenium）……每种方式
   拿到的数据形态、字段、结构都不一样。
2. **导入侧每次重复开发**：历史上每采集一批数据，就手写一个新脚本（`import-boss-data.ts`、
   `import-chat-companies.ts`、`import-chrome-jds.js`、`import-resume-pdf.js`……），
   把「解析数据 → 写入数据库」的逻辑反复重造。

**核心诉求**：把「采集」和「导入」解耦——采集侧怎么拿到数据可以千变万化，但**只要数据能被
整理成一个统一的 JSON 格式，导入就是一条固定、可复用的流程**，无需再写任何导入代码。

---

## 2. 落地方案：统一导入契约 + 通用导入器

### 2.1 设计原则

| 原则 | 说明 |
|------|------|
| **一个文件带全部实体** | 公司/岗位/内推/投递/面试复盘/面经，可只填其中一部分 |
| **幂等** | 重复导入不产生脏数据（见 3.2 去重键） |
| **走正式 HTTP API** | 复用 `import-chrome-jds.js` 的黄金路径，不直连 PGlite |
| **采集与导入解耦** | agent 只负责产出契约 JSON，导入是固定动作 |

### 2.2 两个交付物

1. **`data/import-schema.md`** —— 统一导入契约 v1，逐字段说明 + 示例。
2. **`scripts/import-data.ts`** —— 通用导入器，一条命令入库。

### 2.3 契约 JSON 顶层结构

```jsonc
{
  "meta": { "source": "BOSS直聘", "capturedAt": "2026-11-09" },
  "companies": [],   // 公司档案
  "jobs": [],        // 岗位（同时落 JD + 投递记录）
  "referrals": [],   // 内推信息
  "interviews": [],  // 面试复盘
  "kb": []           // 面经知识库
}
```

`meta` 必填（至少 `source`），其余五个数组可空数组或省略。

### 2.4 用法

```bash
npm run dev                                    # 先起本地服务（dev-login 需要）
node scripts/import-data.ts 数据.json [更多.json ...]
# 环境变量 CA_BASE 可覆盖服务地址（默认 http://127.0.0.1:3000）
```

## 3. 关键实现细节

### 3.1 走正式 HTTP API（黄金路径）

通用导入器**不直连 PGlite**，而是复用 `import-chrome-jds.js` 的已验证模式：

1. `POST /api/auth/dev-login`（`DEV_SKIP_AUTH=true` 时可用）拿会话 cookie，仍是真实 user_id、走 TenantDb；
2. 所有写操作走正式 HTTP API，因此 **0010~0011 触发器、`application_events` 状态流水、
   `change_log` 增量都正常落库**。

> ⚠️ **铁律**：dev 在运行时**绝不能直连 `pgdata`**——PGlite 是进程内 WASM 版 PG，单进程抢写会毁库
> （本项目已三次踩坑，见 `docs/Bug库` 相关记录）。

### 3.2 幂等去重键

| 实体 | 去重键 |
|------|--------|
| 公司 | `name`（已存在则合并 payload，保留原字段） |
| JD | `(companyId, title)` |
| 投递 | `(companyId, position)` |
| 内推 | `(companyName, referrer, position)` |
| 面试复盘 | `(company, position, round)`（无 round 则 (company, position)） |
| 面经 | `title` |

### 3.3 jobs 自动建公司

岗位里只需给 `companyName`，若公司不存在则自动建壳（后续 jobs 补全档案 payload）。

### 3.4 appliedAt 时间线真实

`createApplication` **不写 `appliedAt`**（服务层只在 `updateApplication` 检测到状态变更时才补）。
所以投递要 applied 状态时，通用导入器走两步：
`POST {status:'interested'}` → `PUT {status:'applied'}`，保证 `appliedAt` 与流水时间线真实。

### 3.5 实体 → API 落点对照

| 契约字段 | 数据表 | HTTP 端点 |
|----------|--------|-----------|
| `companies` | `companies` | `POST /api/companies`（存在则 `PUT /:id` 合并） |
| `jobs` | `company_jds` + `applications` | `POST /api/companies/:id/jds` + `POST /api/applications` |
| `referrals` | `referrals` | `POST /api/referrals` |
| `interviews` | `interview_notes` | `POST /api/interview-notes` |
| `kb` | `kb` | `POST /api/kb` |

## 4. 数据采集侧方案（6 条路线）

采集侧与导入侧解耦后，采集本身可根据平台特性自由选路：

| # | 方案 | 适用场景 | 特点 |
|---|------|---------|------|
| 1 | **Agent 浏览器自动化**（WorkBuddy/豆包/TeleAgent） | 变动的、无固定结构的页面（BOSS 聊天、脉脉内推帖） | 灵活，但每次要人盯 |
| 2 | **AI RPA**（影刀/UiBot/自研群控） | 高频、重复、需养号/防风的平台 | 稳定但重，适合批量 |
| 3 | **WebDriver 固定脚本**（Playwright/Selenium） | 结构稳定的官网招聘页（PDD/xTool/唯品会 Moka） | 可重复跑、可 CI 化，首选 |
| 4 | **官方 API / 开放接口** | 有公开 API 的（牛客网、LeetCode 面经、GitHub 内推仓库） | 最干净，零反爬成本 |
| 5 | **RSS / 站点地图订阅** | 招聘官网职位列表页常有 sitemap.xml | 轻量、可定时抓 |
| 6 | **人工/半自动导表** | 数据量小、一次性、来源杂 | 兜底，配合通用导入器 |

**关键判断**：无论用哪种采集方式，最终**只负责产出符合 `data/import-schema.md` 契约的 JSON 文件**，
落到 `data/inbox/`，再 `node scripts/import-data.ts` 一行入库。agent 天然会吐结构化 JSON，这一步近乎零成本。

## 6. 给采集 agent 的落地建议

- **agent 直接产 JSON**：让采集 agent 把抓到的内容按契约输出成 `.json`（agent 天然会吐结构化 JSON），
  落到 `data/inbox/`，再调通用导入器即可，无需写任何导入代码。
- **WorkBuddy Skill 已封装**（2026-11-09）：`~/.workbuddy/skills/career-agent-data-import/`
  —— 采集 agent 在 WorkBuddy 会话里说「把这份数据导入 career-agent」即可自动发现并调用该 Skill，
  无需再写导入脚本。Skill 自包含契约文档副本，跨项目可用。
- **未来平滑升级**：若需外部 agent 直接 push（不经过本地文件），加 `POST /api/import/batch` 端点；
  若需自动化监听，加 `--watch`。两者都与现有通用导入器正交，可独立叠加。
